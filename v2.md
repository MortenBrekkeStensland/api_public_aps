## APS API v2

API v2 is supported by APS 4.0 and later. Fields and commands added after APS 4.0 are marked with their minimum version where relevant. Clients should tolerate unknown fields and missing optional fields so they remain compatible across APS releases and platforms.


### Protocol:
APS has a TCP server that waits for a client connection on a default port (31600) and can be configured from the app settings. Once a connection is instantiated between the client and APS it will continuously listen to the incoming messages from that client.
APS uses length-prefixed JSON messages for all sent/received API traffic. API v1 is no longer supported in current APS versions.

For sending commands
1. Prepare the command as JSON string.
2. Calculate the length of the entire message.
3. Send the length of the entire message in 4 bytes big-endian.
4. Send the JSON string message.

Clients can optionally send an API version message to indicate their supported version:
```JSON
{
   "command": "api_version", 
   "api_version": 2
}
```
APS also will send the API version once the connection instantiated
```JSON
{
   "action": "api_version", 
   "api_version": 2
}
```
APS also sends [`aps_info`](#aps-info) app metadata once the connection is established.
APS 4.3 and later on macOS and Windows also include the current app settings in the full state snapshot sent after connection. See [Settings](#settings) for the payload and the writable subset.

**Notes**

1. All the above messages are length-prefixed.
2. APS expects the API v2 protocol for client communication. If the `api_version` command is omitted, APS still uses the v2 protocol.
3. The `api_version` message is used to report version compatibility between APS and the connected client.



### Commands:

#### Commands structure
```JSON
{
   "command": "...", 
   "parameters": {
      "param1": "...",
      "param2": "...",
   }
}
```
Example:
```JSON
{
   "command": "OpenStart_Presentation", 
   "parameters": {
      "file_path": "C:\\1.pptx",
      "slideNr": 1,
      "isFullscreen": true
   }
}
```

#### Temporary clicker key ownership (Windows)

This optional API v2 addition is available only when `aps_info.data.capabilities`
contains `clicker_key_ownership`. The initial implementation is in Windows APS-PC
development builds; do not infer support from a marketing version. APS-Mac does
not implement it yet. Older commands and clients retain their existing behavior.

An actively listening local client can temporarily own an explicit set of keyboard
inputs. APS leaves the matching unmodified navigation keys to that client, which
captures the physical input and sends ordinary APS commands, including to local
APS. APS does not forward individual clicks. Its other keyboard controls remain
active; injected input and APS-generated replacement keys remain exempt.

```json
{
  "command": "SetClickerKeyOwnership",
  "parameters": {
    "request_id": "f92be8ec-5958-407b-930b-632b020c18a9",
    "sequence": 1,
    "phase": "capture",
    "keys": [{"code_set": "windows_vk", "code": 39, "modifiers": []}],
    "held_keys": [],
    "sampled_at_tick_ms": 120000,
    "sampled_at_counter": 1200000000,
    "expires_at_tick_ms": 123000
  }
}
```

The clocks in this example are illustrative: clients must sample the actual local
Windows clocks. All fields above are required for this new command.

| Field | Meaning |
| --- | --- |
| `request_id` | Nonempty string, at most 64 characters, without control characters; echoed in feedback. |
| `sequence` | Positive integer, increasing on this exact TCP connection. Maximum `9007199254740991`. Successful requests consume their sequence; rejected requests do not renew a lease. |
| `phase` | `capture`, `drain`, or `release`, as described below. |
| `keys` | Complete replacement set, at most 64 unique keystrokes. Each contains `code_set`, integer `code`, and `modifiers`. |
| `held_keys` | Up to 64 unique virtual-key integers currently consumed and held by the client. Used when transferring completion of held presses on release. It does not request navigation. |
| `sampled_at_tick_ms` | Windows `GetTickCount64()` at the snapshot. This is system uptime, not process uptime or a wall-clock timestamp. |
| `sampled_at_counter` | Windows `QueryPerformanceCounter()` at the held-key snapshot (`Stopwatch.GetTimestamp()` on Windows .NET). This distinguishes a physical release that overtakes a handoff within one coarse uptime tick. |
| `expires_at_tick_ms` | Fixed expiry on that same boot clock, strictly in the future and no more than 3,000 ms after the sample or reception. Delayed requests cannot acquire a new three-second interval from their arrival time. |

The initial key namespace is `windows_vk`: codes 8 through 254, excluding Escape
and standalone modifier keys. Modifiers are an unordered, duplicate-free array
drawn from `control`, `alt`, `shift`, and `meta` (the Windows key). Exact combinations
are significant. Other namespaces require a later implementation and are rejected
today; the explicit namespace avoids interpreting future macOS codes as Windows
virtual keys. Clients and servers tolerate unrelated additive object fields.

Reserved Windows combinations are Escape; Ctrl+Left/Right/Up/Down;
Ctrl+Shift+F/K/1/2/3/4/7/8; Alt+Shift+0 through 8; and
Ctrl+Alt+Shift+1 through 6. Reserved input assignments are rejected. Other uses of
modifiers, X, and F13 remain possible. APS's yielding listener applies only to
assigned unmodified Enter, Space, Page Up, Page Down, Left, Up, Right, Down, N, and P.

APS validates the actual TCP peer address against its own interface addresses,
including loopback and normalized IPv4-mapped IPv6. Missing, link-local, and
nonmatching addresses are rejected. Command-supplied addresses and `locality_proof`
are not client-locality authorization. This check proves a directly local socket;
it does not authenticate an executable or protect against a local proxy.

APS replies on the requesting connection only:

```json
{
  "action": "clicker_key_ownership",
  "data": {
    "request_id": "f92be8ec-5958-407b-930b-632b020c18a9",
    "sequence": 1,
    "accepted": true,
    "reason": null,
    "phase": "capture",
    "keys": [{"code_set": "windows_vk", "code": 39, "modifiers": []}],
    "pending_keys": [],
    "expires_at_tick_ms": 123000,
    "expires_in_ms": 2998
  }
}
```

`keys`, `phase`, and expiry describe the requesting connection's actual lease,
including on rejection. A nonowner sees an empty set, `release`, and zero expiry.
`pending_keys` contains virtual keys whose existing presses or recovery guards must
finish before dispatch; a held press must not become another click. `reason` is
`not_local`, `invalid_request`, `stale_sequence`, or `owner_busy` on rejection.
The complete request is accepted or rejected atomically. Another connection cannot
replace or release the owner. Sending a request is not proof of acceptance.

Normal transitions use these phases:

1. Install a prepared consuming listener, then request `capture`. Await matching
   acknowledgement before distributing clicks. APS finishes any presses it already
   consumed and otherwise yields the agreed keys.
2. For stopping, recording, or changing assignments, pause distribution and request
   `drain` with the previous complete set. APS briefly consumes those unmodified
   keys without navigation, finishing any existing press. Keep the client listener
   consuming until the drain is acknowledged.
3. Stop consuming new input, sample held keys, and send `release` with `keys: []`.
   APS resumes ordinary handling while finishing any inherited held presses. A
   later `capture` requires a fresh agreement. An empty set is valid only for
   `release`; other phases require a nonempty set.

Both cooperating hooks allow a consumed key-up to reach the next hook before
returning a consuming result, so either hook order can complete both applications'
held-key state without sending the event to the foreground application.

Ownership ends on disconnect, API shutdown, or the fixed deadline. A client should
renew every second while capture is healthy and stop distributing if an
acknowledgement is missing (Hub uses 750 ms). It must keep consuming through the
outstanding fixed deadline or an acknowledged drain; dropping capture immediately
could allow a local-only advance while APS still yields. Recovery after an uncertain
failure can suppress an ambiguous key until physical key-up, occasionally requiring
a clearing tap. Ordinary acknowledged transitions do not intentionally require one.

Hub checks keyboard-thread responsiveness, recent successful hook installation,
and delivery failures. These checks do not prove continuous physical capture:
Windows can silently remove a timed-out low-level hook. Known failures stop
renewal; periodic replacement provides recovery. No network operations or UI-thread
work occur inside APS's ownership check. Foreground restriction, counter redesign,
and APS-Mac ownership support are outside this initial addition.

#### Locality proof

APS 4.5 and later can prove whether a connected client runs on the same operating-system
machine without transmitting a stable hardware identifier. Support is advertised by the
`locality_proof` entry in `aps_info.data.capabilities`.

After receiving that capability, a client may send:

```json
{
   "command": "GetLocalityProof",
   "parameters": {
      "challenge": "000102030405060708090a0b0c0d0e0f101112131415161718191a1b1c1d1e1f"
   }
}
```

`challenge` must be exactly 32 cryptographically random bytes encoded as 64 lowercase
hexadecimal characters. APS responds with:

```json
{
   "action": "locality_proof",
   "data": {
      "challenge": "000102030405060708090a0b0c0d0e0f101112131415161718191a1b1c1d1e1f",
      "hmac": "5b0a4417bdfd828789a7c1f8187a18cbf12027af14636f43a9c243168d5db66c"
   }
}
```

The response echoes the exact challenge so a client can associate asynchronous feedback
with the correct connection attempt. `hmac` is 32 bytes encoded as 64 lowercase
hexadecimal characters and is calculated as:

```text
HMAC-SHA256(
  key = UTF8(normalizedMachineId),
  message = UTF8("aps-locality-hmac-v1") || hexDecode(challenge)
)
```

APS-Mac uses `IOPlatformUUID` from `IOPlatformExpertDevice`; APS-PC uses `MachineGuid`
from `HKLM\SOFTWARE\Microsoft\Cryptography`. The raw identifier is never sent over the
network. Normalize either source by trimming whitespace, removing one enclosing brace
pair, removing existing hyphens, requiring exactly 32 hexadecimal digits, lowercasing,
and reformatting it as a hyphenated `8-4-4-4-12` UUID. A missing or malformed machine
identifier, challenge, or parameter object produces no `locality_proof` feedback.

Cross-platform test vector:

```text
macOS raw:  A1B2C3D4-E5F6-47A8-90AB-1234567890CD
Windows raw: {a1b2c3d4-e5f6-47a8-90ab-1234567890cd}
normalized: a1b2c3d4-e5f6-47a8-90ab-1234567890cd
challenge:  000102030405060708090a0b0c0d0e0f101112131415161718191a1b1c1d1e1f
HMAC:       5b0a4417bdfd828789a7c1f8187a18cbf12027af14636f43a9c243168d5db66c
```

Clients must generate a new challenge for every connection, accept only the exact
outstanding echoed challenge, and treat an absent or timed-out response as unsupported.
Unknown commands remain ignored by older APS versions.

#### Client identification

This optional API v2 addition is available only when `aps_info.data.capabilities`
contains `client_list`. It exists because several API clients per APS are normal: an
APS Hub, a Companion module, and a remote controller may all be connected at once, and
an operator or support technician needs to see who is connected and what each client
is doing. APS only reports; it never arbitrates between clients. The declared
information is shown in the APS user interface and relayed to every client in the
[`clients`](#connected-clients) feedback so that clients can warn about conflicting
control, for example two sync-group controllers locking the same machine. A client
must not send `ClientInfo`, and must not expect `clients` feedback, when the
capability is absent. Older APS versions ignore the unknown command.

After receiving `aps_info` with the capability, a client may send, at any time:

```json
{
   "command": "ClientInfo",
   "client_kind": "aps-hub",
   "client_id": "9d1c3c2e-6a8f-4d0b-9b2e-3f5a7c1d8e40",
   "client_name": "Morten's MacBook",
   "client_version": "0.1.8",
   "roles": [
      {
         "role": "sync-group",
         "group": "Main room",
         "locked_to_instance_id": "a1b2c3d4-e5f6-47a8-90ab-1234567890cd",
         "locked_to_name": "Lenovo",
         "reference": false
      }
   ]
}
```

The fields are top-level command fields rather than a `parameters` object.

| Field | Requirement | Contract |
| --- | --- | --- |
| `client_kind` | Optional | Short lowercase identifier of the client product. `aps-hub` and `companion` are reserved for APS Hub and the Companion module; other values are free-form. At most 64 characters. |
| `client_id` | Optional | Opaque identifier that is stable per client installation, at most 64 characters. It lets a consumer recognise the same client across reconnections and addresses. |
| `client_name` | Optional | Display name of the client or the computer it runs on, at most 120 characters. Display only. |
| `client_version` | Optional | Client application version, at most 120 characters. Display only. |
| `roles` | Optional | Array of role objects describing what the client is currently doing with this APS. `role` is a required string in each object; the other keys depend on the role. |

The only role defined here is `sync-group`, used by a client that keeps several APS
machines on the same slide:

| Key | Requirement | Contract |
| --- | --- | --- |
| `role` | Required | `sync-group`. |
| `group` | Optional | Human-readable group label, at most 120 characters. |
| `locked_to_instance_id` | Optional | Present when this APS instance is a locked follower in that group. Its value is the `instanceId` of the reference APS instance the client keeps this machine aligned with. |
| `locked_to_name` | Optional | Human-readable name of that reference machine as the client labels it, at most 120 characters. Sent alongside `locked_to_instance_id` so APS can show operators a name instead of an identifier. |
| `reference` | Optional | `true` when this APS instance is the reference that other machines in that group follow. |

A client re-sends the complete `ClientInfo` whenever any field changes, for example
when a sync group is created, locked, or removed. Each message replaces the previous
one for that TCP connection in full; fields omitted from a later message are cleared.
APS stores the latest message per connection, includes it in the
[`clients`](#connected-clients) feedback, and never acts on it: it does not change
which commands the connection may send and it does not restrict other connections.
The information is discarded when the connection closes.

APS must ignore unknown top-level keys, unknown role values, and unknown keys inside a
role object, so that clients can be extended without an API revision. Strings longer
than the limits above are truncated by APS rather than rejected. A malformed
`ClientInfo` is ignored without disconnecting the client. All values are self-declared
by the client; APS does not verify them.

#### Presentation close commands
1. `Navigation_CloseOthers`: Close all other native presentation documents while retaining the current presentation.
   - The command has no parameters.
   - With Speedf selected on Windows, the existing platform-specific behavior closes the active PDF through Speedf's control API and keeps Speedf running; older Speedf builds fall back to application exit.
2. `CloseCurrentPresentation`: Close the native presentation document APS currently reports as displayed, without saving unsaved changes. This command is available when `aps_info.data.capabilities` includes `close_current_presentation`.
   - The target is the same supported native presentation APS uses for `any_presentation_displayed.data.is_any_presentation_displayed` at the time the command is handled.
   - APS closes only that presentation document and leaves its presentation application running.
   - If no supported native presentation matches the displayed state, APS does nothing. A browser or Google Slides presentation is not a native presentation target for this command.
   - The command has no parameters and sends no dedicated success or error response. Clients observe the resulting ordinary presentation-state feedback.

The command names above are established wire names. Clients must send them exactly as documented.

#### Presentation application commands
1. `RestartPowerPoint`: Gracefully quit the running PowerPoint application and reopen it with the same saved presentations, so PowerPoint can load fonts installed while it was running. This command is available when `aps_info.data.capabilities` includes `powerpoint_restart`; absence means the command and its result feedback are unsupported.
   - The command has no parameters. APS reports the outcome through [`powerpoint_restart_result`](#powerpoint-restart-result).
   - On peers advertising `check_presentation_fonts`, remote restart also requires [font checking](#presentation-font-checking-setting) to be ON. While OFF, APS returns `success: false`, `stage: "precheck"`, and `error.code: "font_checking_disabled"` without touching PowerPoint. Turning checking OFF does not interrupt a restart already admitted. Older peers without this capability retain their existing restart behavior.
   - APS never discards edits, never force-quits a PowerPoint process that has a visible window or an open presentation, and never starts a slide show. Reopened presentations open in editing windows. (Windows stops only PowerPoint's empty, windowless leftover process after a successful graceful quit; see the platform note under [`powerpoint_restart_result`](#powerpoint-restart-result).)
   - Guardrails are authoritative on APS, not the client: any full-screen slide show, any unsaved or untitled presentation, or a saved file that is missing blocks the restart before quit with `success: false` and `stage: "precheck"`. APS does not publish an "unsaved changes" state and does not poll PowerPoint for it; clients learn about it only from the result. Clients may additionally disable their own control while `any_presentation_displayed` is true.
   - APS runs one restart at a time for local and remote requests together. A second request while one is running is rejected immediately with `operation_busy` and starts nothing.
   - The APS machine shows no confirmation dialog for a remote request; the requesting client is expected to confirm with its operator.
   - Restart warnings in [font checks](#presentation-font-checks) keep clearing through ordinary `slots` and `watched_presentation_folder` feedback once APS observes the new PowerPoint process; the result does not replace that.

#### Presentation folder commands
1. `SetSelected_PresentationFolder`: Change wathed presentation folder
   - Parameters:
      - bank_number (string | int): it can be "Next", "Previous", or the bank number
2. `CaptureFolder`: Capture current focused presentation's folder and save its path to a bank
   - Parameters:
      - bank_number (int)
3. `SetPresentationFolderPath`: Update a presentation-folder bank by a given full path. Available when `aps_info.data.capabilities` includes `set_presentation_folder_path`.
   - Parameters:
      - bank_number (int)
      - folder_path (string)

4. `Request_FolderManifest`: Discard cached content hashes for the assigned, currently selected presentation bank and start fresh settling/hashing. Available only when `aps_info.data.capabilities` includes `watched_presentation_folder_details`; native [entitlement requirements](#watched-presentation-folder-details) and an active [hashing lease](#temporary-presentation-file-hashing) on the requesting connection apply.
   - Parameters:
      - `bank_number` (required JSON integer): 1 through 20. Strings, booleans, null, missing values, floating-point tokens (including `1.0` and `1e0`) and out-of-range values are rejected.
   - APS never selects a bank for this command. The requested bank must already be assigned and selected.
   - Accepted requests cancel active hash work for that bank/root, clear completed cache entries and restart settling. Hashing still pauses during presentation/webpage preparation and Media Player video playback. Results arrive through ordinary `watched_presentation_folder_details` pushes; there is no dedicated response or request ID.
   - Rejections use diagnostics and existing `notification` feedback (`area: "presentations"`, `level: "warning"`). Notification text is human-readable, broadcast and subject to deduplication; it is not a stable error code or correlated command result.

```json
{"command":"Request_FolderManifest","parameters":{"bank_number":1}}
```

This is an explicit rehash operation, not a polling command. It does not acquire or renew a hashing lease. Connecting alone does not request hashing; a new lease after dormancy starts fresh observation and hashing.

#### Generic notification feedback

The `notification` action is an additive, operator-facing notification channel. APS may send it when `aps_info.data.capabilities` contains `notification_feedback`. Clients must feature-detect that capability; a missing capability means this feedback is unsupported.

Notifications are informational presentation data. A client may display or dismiss them, but it **must not** use `area`, `level`, `message`, other additive fields, or the presence or absence of a notification to block controls, retry an operation, determine readiness, or make another business-critical decision. Any state or operation outcome that clients must interpret programmatically requires its own structured feedback contract.

Only `message` is required. APS can send a simple notification without first defining a code or a component-specific schema:

```json
{
  "action": "notification",
  "data": {
    "message": "The presentation application is responding again."
  }
}
```

A notification can optionally identify its program area and presentation importance:

```json
{
  "action": "notification",
  "data": {
    "area": "media_player",
    "level": "error",
    "message": "APS cannot access media folder 2."
  }
}
```

Fields:

| Field | Requirement | Contract |
|---|---|---|
| `message` | Required | Platform-neutral human-readable text of 1 to 2048 UTF-8 bytes. It contains enough information for a generic client to display the notice without recognizing any other field. |
| `area` | Optional | Open program-area identifier. Initial well-known values are `general`, `presentations`, `media_player`, `still_images`, and `webpages`. An absent or unknown value is presented as a general APS notification. New values do not require an API revision. |
| `level` | Optional | Presentation importance: `info`, `warning`, or `error`. When omitted or unknown, clients use `info`. It is never an instruction to apply control logic. |

Notifications are one-time events sent when the occurrence happens. They are not replayed in the connection snapshot and have no acknowledgement, dismissal, update, or resolution command. Dismissal is local client UI state and does not change APS state. APS should emit a later notification when a recovery is useful to the operator, for example that an unavailable folder is accessible again.

Clients identify the originating APS machine from the connection that delivered the frame. They should record their own receipt time when a display timestamp is useful. APS should avoid repeatedly sending the same unchanged notice in a tight loop; rate limiting and suppression remain implementation details rather than wire state that clients must manage.

Clients must tolerate unknown `area` values and additive fields in the feedback envelope or `data` object. APS-Mac and APS-PC can therefore send new messages from new program areas using this same contract without requiring a public API or client release. A malformed notification should be ignored without disconnecting an otherwise healthy APS connection.

Notification text and additive fields must be safe to expose to a remote operator. APS must not include credentials, licence keys, subscription identifiers, customer data, full filesystem paths, raw platform errors, or other secrets. Prefer a filename or a human-safe label when file context is useful.

Generic notifications do not replace authoritative state feedback or structured operation results. For example, [`media_player_operation_result`](#media-player-operation-result) remains the contract for Media Player selection and load outcomes, and ordinary [`MediaPlayer`](#media-player-feedback) remains the authoritative Media Player state. APS should not also publish a generic notification for the same occurrence. If a future use case requires both forms for compatibility, a separate additive contract must define a shared identifier and which feedback is authoritative.

#### Files Feedback
```JSON
{
   "action": "files",
   "data":{
      "curr": "02.pptx",
      "prev": "01.pptx",
      "next":"-",
      "slide_number": "1",
      "slides_count": "10",
      "presenter_notes": "Welcome the audience and introduce the first topic.",
      "current_build": "0",
      "builds_count": "2",
      "current_build_reliable": true,
      "builds_count_reliable": true,
      "powerpoint_slide_number": "1",
      "powerpoint_slides_count": "10",
      "powerpoint_current_build": "0",
      "powerpoint_builds_count": "2",
      "PowerPoint_media_duration": "00:19:50",
      "PowerPoint_media_current_position": "00:00:05",
      "PowerPoint_media_time_left": "00:19:45",
      "PowerPoint_media_state": "playing"
   }
}
```

- `curr`, `prev`, and `next`: Current, previous, and next presentation filenames. A value of `-` means no file is available.
- `slide_number` and `slides_count`: Current slide and total slide count for the presentation application APS is currently controlling.
- `presenter_notes`: Presenter notes for the current slide. Available in APS 4.3 and later on macOS when APS can read notes from PowerPoint, Keynote, or Google Slides. An empty string or `-` means no notes are available.
- `current_build` and `builds_count`: Current and total animation/build positions where available. Both values are strings. `builds_count` is the number of manual advances the current slide consumes before changing slides; `current_build` is the number already consumed. A slide with no builds reports `"0"` for both. A value of `"-"` means the information is unavailable.
- `current_build_reliable` and `builds_count_reliable`: Optional JSON Booleans that independently qualify the two generic build fields. A numeric build value is published only when its corresponding reliability field is `true`; an unavailable or untrusted value is `"-"` with reliability `false`. Clients may use either reliable value independently, but may use `current_build == builds_count` for build-follow automation only when both fields are `true`. APS-Mac and APS-PC 4.4.0.2 and later emit both Booleans on every `files` message; older APS versions may omit them, so clients must feature-detect their presence.
- `powerpoint_slide_number`, `powerpoint_slides_count`, `powerpoint_current_build`, and `powerpoint_builds_count`: PowerPoint-specific state retained separately from the generic state above. These fields may be absent on older APS versions or unsupported platforms. On Windows they stay `"-"`, or retain the last PowerPoint state, while Google Slides is active. On macOS the two `powerpoint_` build fields currently mirror the generic build fields for PowerPoint, Keynote, and Google Slides. Clients should use the generic fields for the active presentation.

`build_feedback` is implemented on macOS and Windows with the shared contract above. APS-Mac 4.4 and later reports build fields for PowerPoint, Keynote, and Google Slides. APS-PC reports them for PowerPoint and Google Slides; APS-PC 4.4.0.2 is the first Windows version to emit both reliability Booleans on every `files` message. PDFs report `"-"` with both reliability fields `false`. Earlier APS-PC builds may provide numeric PowerPoint or Google Slides build fields without the reliability Booleans; clients retaining compatibility with those builds may feature-detect valid non-negative integer strings only when the fields are absent.

For Google Slides, `builds_count` comes from the deck's server-side model and `current_build` is tracked in present mode. On macOS, `builds_count` is also available while the deck is active in the editor. On Windows, Google Slides build feedback is sent only while APS detects the presentation with its window in the foreground. The total may be `"-"` briefly when a deck is first seen and is refreshed when the slide count changes, when presentation mode starts, and within about a minute of an animation edit. A failed fetch, parse, or periodic revalidation invalidates the cached Windows total rather than leaving it marked reliable.

`current_build` remains `"-"` whenever APS cannot observe manual advances reliably. On macOS this includes missing Input Monitoring permission and Google Slides Presenter View, whose on-screen buttons are not fully observable. On Windows it includes Google Slides Presenter View, an unavailable or degraded keyboard/mouse observer, and a PowerPoint event sink that is missing or being reattached. `builds_count` remains `"-"` whenever APS cannot obtain an exact total, including while a count is resolving, when a presentation cannot be parsed completely, when a Windows PowerPoint `GetClickCount()` read fails, and when PowerPoint on macOS has unsaved changes and only an estimated live effect count is available. A reliable current build may therefore be numeric while the total is `"-"`, or an exact total may be numeric while the current build is `"-"`. The build cursor resynchronizes at slide boundaries; when the total is unavailable, a final observed advance may be published briefly against the departing slide before the slide-number reset arrives.

The `files` feedback is sent when presentation state changes, including every observed animation-build advance. In APS 4.3 and later, Google Slides uses the same `slide_number`, `slides_count`, and `presenter_notes` fields as the other presentation applications.

The generic fields follow the frontmost application: PowerPoint, Keynote, or a Google Slides tab in a frontmost browser report their own presentation, and the selected PDF application in front reports its pages. From APS-Mac 4.5.x and APS-PC 4.5.x, when none of the tracked applications is frontmost (APS itself, Finder or Explorer, or an untracked application) and a PowerPoint slideshow is running (on macOS: exactly one PowerPoint or Keynote slideshow), the generic fields continue to report that slideshow instead of `-`. A browser or the selected PDF application coming to the front still takes over. On Windows the event-driven slide and build updates were already sent regardless of the foreground window; this change aligns the polled snapshot with them. `any_presentation_displayed`, the `slots` opened flags, and `opened_folder_presentation` follow the same rule on both platforms, so they keep describing the running slideshow under this fallback. `active_application` remains foreground-based and reports `null` while an untracked application is frontmost.

Fields specific to PowerPoint media:

> **Note:** These fields are only available when controlling PowerPoint on Windows.

- `PowerPoint_media_duration`: Total media duration (hh:mm:ss).
- `PowerPoint_media_current_position`: Current playback position (hh:mm:ss).
- `PowerPoint_media_time_left`: Remaining time (hh:mm:ss).
- `PowerPoint_media_state`: One of `playing`, `paused`, `stopped`, or `not_ready`.

#### Presentation Preparing Feedback

Available when `aps_info.data.capabilities` contains `presentation_preparation_feedback`. APS-Mac implements this feedback in APS 4.3 and later; APS-PC implements it in APS 4.4.0.1 and later.

Preparing a presentation:

```JSON
{
   "action": "presentation_preparing",
   "data": {
      "is_preparing": true,
      "command_type": "slot",
      "is_fullscreen": true,
      "slot": 1,
      "from": "/Presentations/Opening.pptx",
      "to": "/Presentations/Keynote.key",
      "watched_folder_number": 2,
      "from_watched_folder_index": -1,
      "to_watched_folder_index": 4
   }
}
```

Preparation finished:

```JSON
{
   "action": "presentation_preparing",
   "data": {
      "is_preparing": false,
      "command_type": "slot",
      "is_fullscreen": true,
      "slot": 1,
      "from": "/Presentations/Opening.pptx",
      "to": "/Presentations/Keynote.key",
      "watched_folder_number": 2,
      "from_watched_folder_index": -1,
      "to_watched_folder_index": 4
   }
}
```

- `is_preparing`: Required Boolean. `true` means APS has accepted a presentation start or switch request and the requested presentation is not visible on the presentation output yet. `false` means no preparation is currently in progress.
- `command_type`: Present on operation feedback. One of `direct_path`, `slot`, `next`, or `previous`. A direct path that also belongs to the watched folder remains `direct_path`; watched-folder membership does not change the command type.
- `is_fullscreen`: Present on operation feedback. The effective Boolean fullscreen choice for the operation.
- `slot`: Optional 1-based presentation slot number. It is present only when `command_type` is `slot`.
- `from`: Optional normalized absolute path of the presentation APS is switching away from. It is omitted when there is no previous presentation or APS cannot determine its path.
- `to`: Optional normalized absolute path of the presentation APS is preparing. For direct-path and slot commands it is normally present in the first preparing message. For next/previous navigation it may be omitted initially and added or replaced in a later `is_preparing: true` update after APS resolves the exact target.
- `watched_folder_number`: Optional 1-based selected presentation-folder bank captured when preparation starts.
- `from_watched_folder_index` and `to_watched_folder_index`: Zero-based positions matching the captured `watched_presentation_folder.files_list`. The corresponding field is present whenever its path is known and is `-1` when that path is not in the captured watched folder. Path identity, rather than filename alone, is used, so duplicate filenames in different directories remain distinct.

APS sends normalized absolute paths in `from` and `to`. Clients must replace their stored preparation context with every new `presentation_preparing` frame because an active frame can add or change the resolved target. Network commands and equivalent actions from the local APS user interface use the same feedback contract.

When Seamless Switching displays a screenshot cover, `is_preparing` remains `true` until both the presentation operation has reached its ready point and the cover has been removed. If Seamless Switching is disabled, unavailable, or its capture fails, the ready point alone ends the interval. APS sends the current state in the initial connection snapshot after advertising the capability; an idle snapshot contains only `is_preparing: false`.

Active updates and the final `is_preparing: false` edge retain all available operation context. The false edge reports that the preparation interval has ended; it is not a structured success result and must not be interpreted as proof that the requested presentation opened successfully. Commands that do not select a new presentation, such as `Navigation_CloseOthers`, `CloseCurrentPresentation`, escape, slide/build/section controls, and `Navigation_CurrentFS`, do not start this feedback. Google Slides uses [webpage preparation feedback](#webpage-preparation-feedback) instead.

#### PowerPoint Sections Feedback

Available in APS 4.3 and later on macOS. This feedback describes the sections in the PowerPoint presentation currently running as a slideshow.

```JSON
{
   "action": "powerpoint_sections",
   "data": {
      "available": true,
      "current_section_index": 2,
      "current_section_id": "id-2",
      "current_section_name": "Main section",
      "current_slide_in_section": 1,
      "sections_count": 2,
      "sections": [
         {
            "id": "id-1",
            "name": "Default Section",
            "first_slide_index": 1,
            "slides_count": 2
         },
         {
            "id": "id-2",
            "name": "Main section",
            "first_slide_index": 3,
            "slides_count": 2
         }
      ]
   }
}
```

- `available`: `true` when APS has section information for the active PowerPoint slideshow. An available presentation may legitimately contain zero sections.
- `current_section_index`: The current 1-based section index, or `-1` when the displayed slide cannot be mapped to a section.
- `current_section_id`: PowerPoint's opaque identifier for the current section, or `-` when unavailable.
- `current_section_name`: The current section name, or `-` when unavailable.
- `current_slide_in_section`: The displayed slide's 1-based position within its section, or `-1` when unavailable.
- `sections_count`: The number of section records in `sections`.
- `sections`: Presentation-ordered PowerPoint section records. A record's 1-based position in the array is its section index. Each record contains its opaque `id`, `name`, absolute 1-based `first_slide_index`, and `slides_count`.

When section information is unavailable, APS sends `available: false`, an empty `sections` array, `sections_count: 0`, `-1` for unavailable numeric current fields, and `-` for the current section ID and name. This clears stale client state when PowerPoint closes or leaves slideshow mode.

If APS cannot read any section record completely, it reports section information as unavailable instead of sending a partial section list.

The feedback is sent when section metadata, the current section position, or PowerPoint slideshow availability changes. It is also included in the full state snapshot sent after a client connects.

#### Media Player operation result

When `aps_info.data.capabilities` contains `media_player_operation_result`, APS publishes the outcome of each Media Player selection or load attempt. The same platform-neutral error message is used by the local APS user interface and sent over the network.

Selection failure:

```json
{
  "action": "media_player_operation_result",
  "data": {
    "success": false,
    "operation": "select",
    "slot": 3,
    "filename": "clip.mxf",
    "error": {
      "code": "unsupported_file_type",
      "message": "This file type is not supported.",
      "details": {
        "file_extension": "mxf"
      }
    }
  }
}
```

Successful load:

```json
{
  "action": "media_player_operation_result",
  "data": {
    "success": true,
    "operation": "load",
    "slot": 3,
    "filename": "walk-in.mp4",
    "error": null
  }
}
```

- `success`: `true` when the selection or load succeeded; otherwise `false`.
- `operation`: `select` when assigning, replacing, or clearing a Media Player slot; `load` when preparing a slot for playback.
- `slot`: The 1-based Media Player slot number, or `null` when no valid slot can be identified.
- `filename`: The filename without its parent path, or `null` when no file can be identified. Clients must not treat this field as a usable filesystem path.
- `error`: `null` on success; otherwise an object containing a stable `code`, a human-readable `message`, and an optional `details` object. Clients must use `code`, not `message`, for program logic. Unknown additive fields and error codes must be tolerated.
- `error.details`: Optional platform-neutral string values that provide safe diagnostic context. Currently defined keys are `file_extension`, containing the lowercase extension without a leading dot, and `blocked_by`, containing `active_playback` or `automatic_loading`.

Error codes:

- `invalid_slot`: The requested slot is missing, malformed, or outside the supported range.
- `empty_slot`: The requested slot has no assigned media, or no assigned media is available for a Next/Previous load.
- `unsupported_file_type`: The selected file extension is not supported as video, audio, or image media.
- `file_not_found`: The assigned file no longer exists or cannot be found.
- `file_not_readable`: The file exists but APS cannot read it.
- `media_not_playable`: The file was found and read, but the media framework could not open it. The file may be damaged or use an unsupported codec.
- `operation_blocked`: APS rejected the operation because of current state, such as changing the active playing/paused slot or loading while an automatic load is pending.
- `internal_error`: APS could not complete the operation for another internal reason.

This is event feedback, not a request-correlated response: the payload has no command or request identifier, and local APS activity can also produce it. A client that initiated an operation may use `operation`, `slot`, and `filename` as context, but must continue to treat the ordinary [`MediaPlayer`](#media-player-feedback) message as the authoritative playback and slot state. Load results can arrive asynchronously after AV media validation. Older APS builds continue to work without this message; clients must feature-detect `media_player_operation_result` and retain their existing timeout or state-feedback behavior when it is unsupported.

This platform-neutral contract is implemented by APS-Mac and APS-PC.

#### PowerPoint restart result

When `aps_info.data.capabilities` contains `powerpoint_restart`, APS publishes one `powerpoint_restart_result` message per [`RestartPowerPoint`](#presentation-application-commands) attempt. As with `media_player_operation_result`, the message is published for remote *and* local restart attempts: the local APS user interface and the network report the same outcome. It is not replayed in the connection snapshot.

Successful restart:

```json
{
  "action": "powerpoint_restart_result",
  "data": {
    "success": true,
    "stage": "restore",
    "reopened": ["Talk.pptx", "Walk-in.pptx"],
    "not_reopened": [],
    "error": null
  }
}
```

Blocked before quit:

```json
{
  "action": "powerpoint_restart_result",
  "data": {
    "success": false,
    "stage": "precheck",
    "reopened": [],
    "not_reopened": [],
    "error": {
      "code": "unsaved_changes",
      "message": "Save changes to “Talk.pptx” before restarting PowerPoint."
    }
  }
}
```

- `success`: `true` when the PowerPoint application exited and a new process started. A partial reopen is still `success: true` with entries in `not_reopened`.
- `stage`: Where the attempt ended: `precheck`, `quit`, `relaunch`, or `restore`.
- `reopened`: Filenames (not paths) reopened for editing in the new process.
- `not_reopened`: Filenames the operator must reopen manually, for example slideshow-format files (`.pps`, `.ppsx`, `.ppsm`) or files missing after quit.
- `error`: `null` on success; otherwise an object containing a stable `code` and a human-readable `message`. `message` is platform-neutral, safe for remote display, and contains no full paths or raw automation errors. Clients must use `code`, not `message`, for program logic, and must tolerate unknown codes and additive fields.

Error codes:

- `font_checking_disabled`: Presentation font checking is OFF, so APS refused this remote restart before touching PowerPoint. Applies to peers advertising `check_presentation_fonts`.
- `slideshow_running`: A full-screen PowerPoint slide show is running.
- `unsaved_changes`: An open presentation has unsaved changes.
- `untitled_presentation`: An open presentation has never been saved to a file.
- `file_missing`: A saved presentation's file is unavailable on disk.
- `powerpoint_not_running`: PowerPoint is not running, or exited before APS could ask it to quit.
- `multiple_instances`: More than one PowerPoint process is running.
- `automation_denied`: APS is not permitted to control PowerPoint (macOS Automation permission, or Windows COM access denied).
- `operation_busy`: Another restart attempt, local or remote, is already in progress.
- `quit_timed_out`: PowerPoint did not exit within the graceful-quit wait (20 seconds); APS did not force-quit it or discard changes.
- `relaunch_failed`: PowerPoint exited but a new process could not be started or verified. `not_reopened` lists every file to reopen manually.
- `internal_error`: APS could not complete the attempt for another internal reason.
- `protected_view_open` (Windows only): A PowerPoint Protected View window is open. Close it, then retry. macOS never sends this code.

This is event feedback, not a request-correlated response: the payload has no command or request identifier, and local APS activity can also produce it. Older APS builds continue to work without this message; clients must feature-detect `powerpoint_restart`.

`powerpoint_restart` is implemented on macOS and Windows with the same command, result envelope and error codes. On Windows, PowerPoint keeps an empty, windowless automation process behind after a successful graceful quit (every presentation is already closed by then); APS stops that process so the new PowerPoint can start. APS never force-quits a PowerPoint process that has a visible window or an open presentation. Clients must feature-detect the capability rather than infer support from the platform.

#### Office Font Check

When `aps_info.data.capabilities` includes `office_font_check`, an operator can
explicitly request a scan of the local Office font cache:

```json
{"command":"CheckOfficeFonts","parameters":{"request_id":"hub-123-abc"}}
```

`request_id` is required: 1–128 ASCII letters, digits, hyphens or underscores.
Use a fresh ID for each attempt. Invalid or missing IDs are ignored without
accessing Office folders. There are no path or font-name parameters: the scan
covers the local cache and updates the same machine/user evidence as APS's native
action. It does not download/install fonts, launch PowerPoint or alter presentations.

**Font checking must be ON.** On peers advertising `check_presentation_fonts`,
require its authoritative Boolean [setting](#presentation-font-checking-setting)
before offering a scan. While OFF, APS immediately returns `unavailable` with
`reason: "font_checking_disabled"` and the supplied `request_id`; it does not activate
APS or access Office folders. Do not turn the setting on automatically to service a
scan request. The disabled response takes precedence over the presenting guard
below. Missing capability on an older peer does not mean checking is OFF.

**Not while presenting.** The scan brings APS to the front and can raise a macOS
permission popup, so APS refuses the command while `is_any_presentation_displayed`
is true (including a fullscreen webpage) or a Media Player video is playing.
Nothing is scanned, APS is not activated, and the request receives only an
immediate terminal `blocked` result. Clients should apply the same rule from
[`any_presentation_displayed`](#any-presentation-displayed) and Media Player feedback
before sending, so the operator sees the reason without a round trip. Retry
explicitly when nothing is being presented. The local scan in APS's own Fonts view
is not blocked.

**Permission remains local.** Tell the operator before sending the command that
any macOS popup asking to let APS access other apps' data must be accepted on the
target Mac for the check to work. APS activates itself to make the permission
interaction visible. Permission may already be granted, so a popup is not guaranteed.
Never trigger this command automatically from startup, reconnect, inventory refresh,
a warning, or polling. A user action is required for every attempt; do not retry
silently after a timeout or disconnect.

APS publishes `office_font_check_result` events with the supplied ID:

```json
{"action":"office_font_check_result","data":{"request_id":"hub-123-abc","status":"checking","message":"Checking Office fonts. If macOS asks for permission, accept the popup for APS on this Mac so the check can finish."}}
```

| `status` | Meaning |
| --- | --- |
| `checking` | The explicit scan has started; it may be waiting for local permission. |
| `complete` | The scan finished and evidence was saved. Fonts can still be absent; this is not a claim that all presentation fonts were verified. |
| `unavailable` | Font checking is OFF (`reason: "font_checking_disabled"`), or the scan could not finish or evidence could not be saved. Read the reason/message and resolve the setting or access on the Mac before retrying explicitly. |
| `cancelled` | The scan was cancelled in APS, including when font checking was turned OFF locally or remotely. Partial results may exist. |
| `busy` | Another local or remote Office check is running. This request did not start another scan. |
| `blocked` | APS refused the request because a presentation or video is on screen. No scan started. |

Results may carry an optional `reason`:

| `reason` | `status` | Meaning |
| --- | --- | --- |
| `font_checking_disabled` | `unavailable` | Check presentation fonts is OFF. No scan started. |
| `presentation_displayed` | `blocked` | A PowerPoint or Keynote slideshow, active PDF presentation, or fullscreen webpage is showing. |
| `video_playing` | `blocked` | A Media Player video is playing. |

```json
{"action":"office_font_check_result","data":{"request_id":"hub-123-abc","status":"unavailable","reason":"font_checking_disabled","message":"Font checking is off in APS. Turn on Check presentation fonts, then retry."}}
```

```json
{"action":"office_font_check_result","data":{"request_id":"hub-123-abc","status":"blocked","reason":"presentation_displayed","message":"APS did not start the full font scan because a presentation is showing on this Mac. The scan brings APS to the front and can show a macOS permission popup. Try again when nothing is being presented."}}
```

Treat an unknown or missing `reason` as a generic refusal and show `message`.

`message` is human-readable plain text. A request receives `checking` and then one
terminal result, or an immediate `unavailable`, `busy` or `blocked`. These events are broadcast to connected
clients and are not replayed in snapshots; match `request_id` before updating your
own operation. A result for another request must not finish the pending operation.
A lost connection or timeout does not cancel the native scan and must not be
reported as successful verification. The native Cancel action remains available.
Turning font checking OFF cancels an active scan and ends its accepted request with
`cancelled`; do not treat it as a completed verification.

Presentation warnings refresh through ordinary `slots` and
`watched_presentation_folder` feedback after the scan. Clients must wait for that
feedback rather than clearing warnings when a `complete` event arrives. Positive
saved evidence, incomplete/cancelled scans, and restart advice retain the rules in
[Presentation Font Checks](#presentation-font-checks).

Implemented on APS-Mac. APS-PC does not advertise `office_font_check` or implement
this command; Windows checks its font sources through its existing checker and has
no matching macOS permission prompt. Hub running on either OS can request the check
on a capable Mac. Older APS versions remain usable without this action. Always
feature-detect the capability, rather than inferring it from the platform/version.

### Presentation Font Checks

Feature-detect `presentation_font_checks` in `aps_info.data.capabilities`. This
additive API v2 feature is implemented in APS-Mac and APS-PC development source.
Do not infer support from a marketing version or platform. Older clients can
ignore the new field; clients receiving older peers must tolerate its absence.

The existing `slots.data` and `watched_presentation_folder.data` objects include
an optional `font_checks` array, with exactly one entry per `filenames` or
`files_list` entry, respectively, in the same order. Associate each check with the
inventory in that same message; if a client sorts files, move their checks with
them. The selected watched folder is the only folder covered. With no selected
folder, `number` is `-1`, and `files_list` and `font_checks` are empty.

The separate [font-checking setting](#presentation-font-checking-setting) controls
whether capable APS builds perform these checks. When `check_presentation_fonts` is
advertised and its setting is OFF, clear cached font warnings and restart advice,
and show that checking is off. APS-Mac reports `unavailable` with empty warnings
for supported presentation formats; empty slots and unsupported formats still use
`not_applicable`. These are not successful empty checks. Missing capability on an
older Mac or current APS-PC preserves its existing checking behavior.

Each check is an object, for example:

```json
{
  "status": "complete",
  "warnings": [
    "Missing fonts: Example Sans",
    "Preview/print-only embedded fonts: Example Serif"
  ]
}
```

| Field | Meaning |
| --- | --- |
| `status` | String: `pending`, `complete`, `unavailable`, or `not_applicable`. |
| `warnings` | Array of human-readable strings, using the same warning text as native APS. May be empty. Render as plain text, not HTML. |
| `powerpoint_restart_required_fonts` | Optional array of font-name strings. APS-Mac and APS-PC report fonts used by this presentation that became available after being observed missing while a PowerPoint process was running. Empty means no restart requirement was observed; absence means this detail is unsupported or unknown. Keynote and other non-PowerPoint checks return an empty array. |

- `pending`: A supported presentation has no accepted result yet, or changed
  during reading. An empty warnings array does not mean a successful check.
- `complete`: The check completed, with zero or more warnings. Empty warnings
  means no warning was detected, not a guarantee of rendering fidelity.
- `unavailable`: The presentation needs downloading, cannot be read, or could
  not be extracted/parsed. Warnings explain the issue without raw platform errors.
  APS-Mac also uses this existing status with empty warnings while font checking
  is OFF; use the setting below to distinguish disabled checks from read failures.
- `not_applicable`: An empty slot or unsupported file type. No font warning footer
  is needed. Both platforms check `.pptx`, `.pptm`, `.ppsx`, and `.ppsm`.
  APS-PC additionally checks `.potx` and `.potm`. Current APS-Mac development
  source additionally checks modern Keynote `.key` files (ZIP or directory
  packages); Keynote is not checked on APS-PC. PDF and legacy `.ppt` files are
  not checked on either platform. Older APS-Mac builds may advertise
  `presentation_font_checks` but still return `not_applicable` for Keynote;
  honor each entry's status rather than assuming identical format coverage.

PowerPoint warnings distinguish missing slide fonts, Office cloud-font availability,
fonts used only in notes, unresolved theme references, and restricted or preview/print
embedded fonts. Office warning wording varies by platform and build; older builds
may describe a font as requiring an Office cloud download.

Current APS-Mac development source uses a bundled public Microsoft Office font list
to classify fonts that are not otherwise available or embedded. Membership in that
list does not establish local availability. Without local evidence, the warning is,
for example, `Aptos Display: Office cloud font—availability not verified`. The check
can still be `complete`: presentation inspection has finished, even though Office
font availability remains unverified. An incomplete or cancelled Office check is
also expressed in warning text, not a new status or the presentation-level
`unavailable` status.

APS-Mac startup, inventory refreshes and ordinary font rechecks do not read Office's
protected font folders. Turning **Check presentation fonts** ON, the native
**Check Office fonts** / **Recheck Office fonts** actions, and an explicit
[`CheckOfficeFonts`](#office-font-check) command initiate that access, which may
require a macOS permission decision on the APS machine. Restoring a saved ON
preference at startup does not repeat the protected Office scan.
These actions inspect local font files; they do not download fonts or launch
PowerPoint. Per-presentation structured Office verification-state and timestamp
fields remain local. Human-readable warnings may mention the date of previous
verification; clients must not parse that text.

Successful Office checks save positive evidence locally for that Mac and user.
APS-Mac reuses it after relaunch without reopening Office's folders, and it has no
automatic expiry. A positive suppresses the missing/unverified warning; the native
UI retains an informational row with the verification date and a recheck action.
This is historical evidence: a font removed later can remain reported as available
until an explicit recheck conclusively finds it absent. Denied, incomplete or
cancelled checks retain any earlier positive and report the failed check in warning
text. A conclusive absence revokes the positive; negative outcomes are not persisted.
The bundled public list may be incomplete, so an unlisted Office font can still
receive an ordinary missing-font warning. None of these outcomes guarantees
PowerPoint rendering fidelity.

Keynote checks **document-wide font references**, including unused styles and layouts as well
as styles used by slide content, notes, tables, charts, captions and bullets.
A missing Keynote font reference does not establish that a visible slide will
change. For example:

```json
{
  "status": "complete",
  "warnings": [
    "Missing fonts: Example Sans",
    "Includes fonts in unused styles and layouts."
  ]
}
```

APS-Mac and APS-PC also report fonts pending a PowerPoint restart through the
existing `slots` and `watched_presentation_folder` LAN feedback. For example, after a
previously missing font is installed while PowerPoint remains open:

```json
{
  "status": "complete",
  "warnings": [
    "Fonts pending PowerPoint restart: Example Sans"
  ],
  "powerpoint_restart_required_fonts": ["Example Sans"]
}
```

The check remains `complete`: this is restart advice, not the `pending` status
used for an unfinished check. Closing/reopening only the presentation or
rechecking fonts does not clear the advice. APS-Mac listens for PowerPoint
launch/quit notifications; APS-PC checks PowerPoint process identity (process ID
and start time) during font checks and its existing periodic sweep. For this
restart advice, neither platform inspects PowerPoint's live internal font state.
APS-Mac does not infer a restart requirement from historical Office evidence or
unverified Office availability; a conclusive missing-to-present observation in the
current APS session follows the existing restart rules. When the affected PowerPoint
process quits, APS rechecks and pushes ordinary feedback with the restart list
empty and that warning removed;
the next launch starts a fresh observation. If another affected PowerPoint
process is still running, its advice remains. Fonts embedded in the presentation
do not require this warning. Keynote is excluded from restart tracking.

This is conservative, memory-only advice based on transitions APS observes while
running, not proof of PowerPoint's internal font state. It cannot reconstruct
installations that happened while APS was closed, and restarting APS clears its
observation history. Older peers may advertise `presentation_font_checks` while
omitting `powerpoint_restart_required_fonts`; tolerate the missing field and do
not interpret it as proof that a restart is unnecessary. No new command or
subscription is required. Clients should replace this list with each incoming
check, including clearing it on an empty list or removing stale advice when the
field is absent.

Keynote availability uses locally available macOS fonts, including local document
fonts resolved through CoreText. Fonts found only in PowerPoint's private bundle
or Office cloud cache, and downloadable-only fonts, do not count as available to
Keynote. The check does not launch Keynote or request font downloads. Locked,
legacy XML, unsupported, damaged or over-limit Keynote documents return
`unavailable`, not a successful check with empty warnings.

All warnings are advisory display text: do not parse them as stable codes,
disable controls, retry commands, or derive readiness or cross-machine file
verification decisions from them. Embedded-font permission warnings are not
detection of the presentation's live read-only state.

Initial connection snapshots contain current cached checks. APS pushes ordinary
`slots` and `watched_presentation_folder` messages when results change, including
when warnings clear, even if the inventory and opened flags are unchanged. Replace
annotations with the incoming snapshot; clear obsolete annotations on slot/file
replacement, folder changes and reconnects to unsupported peers. Tolerate unknown
statuses and additive fields. Missing, malformed or mismatched checks must not be
shown as successful checks or associated with unrelated files.

Results describe the last accepted background observation on the reporting APS
machine, not the Hub/client machine's installed fonts. An existing result remains
visible while a background recheck runs, unless checking is turned OFF. On peers
with the font-checking setting, the following automatic work runs only while ON.
APS checks assigned slots and the
selected folder at startup, after inventory changes, and through the existing
periodic inventory refresh (a 30-second sweep on APS-PC); on APS-Mac registered
system-font changes reload availability, and on both platforms a completed
[remote font installation](#remote-font-installation) rechecks the retained
results. Presentation results are memory-only; APS-Mac's saved positive Office
evidence is the exception for font availability described above. APS-Mac Office
cache changes require the explicit local Office recheck action: an ordinary refresh
or APS restart reuses saved evidence without inspecting that cache. Other font-source
changes may require a local manual recheck or restart. PowerPoint Chart/SmartArt
font usage and localized font-name matching are not fully covered.
Keynote checks stored font references rather than resolving visible text, font
traits or per-glyph fallback; exact parity with Keynote's private missing-font
rules across versions is not guaranteed. A completed check is therefore not proof
that the presentation will render exactly as intended.

No new command or polling is required. This feedback does not require a hashing
lease or file-verification entitlement and is independent of
`watched_presentation_folder_details`. Existing presentation commands are unchanged.

#### Temporary Presentation File Hashing

Feature-detect `presentation_file_hashing_control` in `aps_info.data.capabilities`, alongside `watched_presentation_folder_details` and `license_status`. This API v2 feature is identical on APS-Mac and APS-PC. It is generic: APS Hub uses it for Presentation Sync group members, and other network clients may request it for their own verification workflows. `ClientInfo` declarations remain descriptive and do not enable hashing.

Hashing is **OFF and fully dormant by default**. It has no persistent preference or native settings switch. A request applies to its exact TCP connection, never to a declared client ID or IP address.

```json
{"command":"SetPresentationFileHashing","parameters":{"enabled":true,"request_id":"hash-1"}}
```

- `enabled`: required JSON boolean. `true` acquires or renews a 30,000 ms lease; `false` releases only this connection's lease.
- `request_id`: required string of 1–64 ASCII characters from `A-Z`, `a-z`, `0-9`, `.`, `_`, `:`, `-`. Echoed for correlation; repeated valid enable requests renew the lease. Unknown additive fields are ignored.
- Renew every 10 seconds while interested. APS uses its own monotonic deadline and expires leases independently of hash work and incoming messages. Unrelated commands and outgoing feedback do not renew a lease.
- Enable requires native `license_status` with exactly `state: "licensed"` and `will_close: false`, and APS must be awake. Disable remains allowed when unlicensed or asleep. Invalid requests do not activate or renew anything.
- APS hashes the currently selected presentation bank while any eligible connection holds a lease. Another connection's release cannot disable an existing lease. Adding clients and renewing leases do not restart the worker.
- Detected disconnect immediately removes that connection's lease. Silent network failure or a frozen client expires within 30 seconds of its last accepted renewal. Listener shutdown, app restart, entitlement loss and system sleep clear leases; waking does not restore them. Delayed work cannot recreate a closed connection's lease.

APS acknowledges each command to the requesting connection before delivering its newly enabled details. All API v2 connections receive initial state and subsequent lifecycle changes:

```json
{"action":"presentation_file_hashing","data":{"request_id":"hash-1","accepted":true,"reason":null,"lease_active":true,"lease_remaining_ms":30000,"enabled":true}}
```

| Field | Meaning |
| --- | --- |
| `request_id` | Correlation string, or `null` for unsolicited state or an invalid request ID. |
| `accepted` | `true` for an accepted command, `false` for a rejected command, `null` for unsolicited state. |
| `reason` | `null`, or rejection reason `invalid_request`, `not_licensed`, `sleeping`. |
| `lease_active` | Whether this recipient connection currently owns a valid lease. |
| `lease_remaining_ms` | Integer 0–30,000; positive exactly when this connection's lease is active. |
| `enabled` | Whether any client enables hashing globally. This describes demand, independent of preparation/video pauses or folder availability. |

For unsolicited state, `request_id`, `accepted` and `reason` are all `null`. A nonowner can see `enabled: true` with `lease_active: false`; it cannot use that as its own authorization. Remaining time is sampled when feedback is generated. Clients must correlate acknowledgements, enforce a conservative local deadline measured from request send time, and discard verification evidence on release, expiry or connection replacement. Sending a command alone does not prove acceptance. Unknown feedback fields must be ignored.

When the last lease ends, APS stops hash-specific watching, reconciliation, settling, package traversal and cache work. It cancels between chunks and package entries; an already-blocked filesystem read can finish later, but cannot publish an obsolete result or start another read. Ordinary presentation-folder observation and controls continue unchanged. First activation starts a new watcher before enumeration and performs fresh settling/hashing. Only continuously observed content may reuse in-memory hashes; old persisted hash caches are not loaded or written. Bank/root changes, restart and dormancy discard that cache trust. Transfer-integrity SHA-256 checks remain mandatory and independent.

Hashing was not publicly released before this opt-in contract. No compatibility activation from older development clients is provided. Released clients' ordinary controls and legacy folder feedback retain their existing behavior; clients without this capability use filename comparison.

#### Watched Presentation Folder Details

Available only when `aps_info.data.capabilities` contains `watched_presentation_folder_details`. This additive feature is implemented in APS-Mac and APS-PC source. Do not infer support or a minimum released version from marketing version numbers. Feature-detect each capability.

The details capability covers both this feedback and [`Request_FolderManifest`](#presentation-folder-commands). It advertises implementation support independently of licensing. Details delivery and manual rehash require native [`license_status`](#licence-status) with `state: "licensed"` and `will_close: false`. Trial, unknown and closing states do not qualify. Details also require an active hashing lease owned by the recipient connection. Becoming licensed alone does not enable hashing. Entitlement loss clears all leases and cached verification evidence. Clients never receive licence keys or perform licence validation.

Only the currently selected presentation bank is monitored while a hashing lease exists. A newly subscribed connection receives the current snapshot if another lease has kept observation active; otherwise activation starts fresh settling and hashing. Changed details are pushed with a 250 ms coalescing window; unchanged periodic pushes are not sent. Clients must still tolerate unchanged snapshots being resent.

The existing [`watched_presentation_folder`](#watched-presentation-folder) action, full paths, filtering, natural ordering and navigation indices remain unchanged. Details use basenames and unsigned UTF-8 byte ordering: **indices in `data.files` are not presentation-navigation indices**. Join details to the current legacy inventory by exact basename and bank identity; do not normalize case or Unicode. These independently delivered frames can arrive in either order. Do not combine details with a different bank or stale inventory.

```json
}
```

The tiny contents in this example are digest test vectors, not valid presentations. Ordinary production files are hashed in their entirety without parsing their format.

| Field | Contract |
| --- | --- |
| `number`, `name` | One-based selected bank number and existing folder-name convention. No selected/assigned bank uses `-1` and `""`. An assigned but unavailable root retains its bank identity. |
| `files` | Eligible immediate children of the selected bank, sorted by unsigned UTF-8 filename bytes. Ordinary subdirectories are not recursively inventoried. |
| `filename` | Basename including extension, preserving original case and Unicode representation; never a full path. |
| `size` | Integer bytes, or explicit JSON null when unavailable. For directory-form packages, the sum of regular descendant file sizes. |
| `mtime` | UTC RFC 3339 string with exactly nine fractional digits, or explicit JSON null: `YYYY-MM-DDTHH:mm:ss.nnnnnnnnnZ`. Windows retains FILETIME precision, with two trailing zeros for 100 ns precision; the underlying filesystem may be coarser. |
| `sha256` | 64 lowercase hexadecimal characters when ready; explicit JSON null otherwise. |
| `hash_state` | `pending`, `ready` or `error`. |
| `hash_error_code` | Optional per-file explanation when `hash_state` is `error`. `"cloud_download_required"` means native filesystem evidence says content must be downloaded before it can be hashed. Omitted otherwise. Missing, null, unknown or unusable values must not invalidate otherwise valid feedback or imply online-only availability. Ignore this field outside `error`. |
| `is_package` | Optional; present only as `true` for directory-form `.key` entries. Absent for ordinary files, including ZIP-form `.key`. Windows production inventory does not currently admit Keynote files or packages. |
| `folder_digest` | Aggregate SHA-256 defined below when the folder is ready; explicit JSON null otherwise. |
| `folder_digest_state` | `error` when the folder is unavailable/unassigned or any entry is in error; otherwise `pending` when any entry is pending; otherwise `ready`. Error takes precedence over pending. |

An accessible empty folder reports `ready` and the SHA-256 of empty input. An unavailable/unassigned folder reports an empty `files` array, null digest and `error`; it must not be interpreted as a successful empty-folder comparison.

Platform eligibility preserves existing behavior. Mac admits lowercase `pptx`, `ppt`, `ppsx`, `pps`, `pptm`, `ppsm`, `key` and `pdf` extensions and excludes filenames containing `~`, such as Office owner files (`~$Deck.pptx`) and editor backups (`Deck~.pptx`); the directory path is not inspected, so cloud containers such as iCloud Drive's `com~apple~CloudDocs` are eligible (APS-Mac builds before 13 September 2026 excluded any path containing `~`). Windows admits immediate files with case-insensitive `.ppt`, `.pptx`, `.pptm`, `.pps`, `.ppsx`, `.ppsm` and `.pdf` extensions; PowerPoint basenames beginning `~$` are excluded, while the existing PDF filter does not exclude them. Windows does not admit `.key` files or ordinary directories. Hidden files are not excluded merely because they are hidden. Admitted unsupported filesystem objects or links produce errors rather than being followed. This extension does not unify platform filename eligibility or add Keynote playback on Windows.

##### Online-only content

An online-only placeholder retains the existing API v2 fallback:

```json
{
  "filename": "Talk.pptx",
  "size": null,
  "mtime": null,
  "sha256": null,
  "hash_state": "error",
  "hash_error_code": "cloud_download_required"

```

Metadata may be present when already known. The folder digest remains null with
`folder_digest_state: "error"`. This optional explanation needs no new command or
capability: older clients continue to see `error`; newer clients may display
**Online-only** and **Make the file available offline in your sync app to verify
its contents.** It does not prove equal contents, successful sync delivery, local
playability or show readiness. Independent missing-file, content-mismatch,
offline-machine and unrelated read errors must remain visible.

Windows uses native `Offline`, `RecallOnOpen` or `RecallOnDataAccess` attributes on
otherwise supported filesystem objects. Hydrated cloud reparse tags alone are not
evidence; symlinks, junctions and unsupported reparses remain ordinary errors.
macOS uses `SF_DATALESS` from `lstat`/`fstat` for regular files and directories,
including a directory-form Keynote package or a descendant needed for its hash.
A dataless descendant makes the outer package online-only. Cloud-managed paths,
provider names, aliases and package status alone never establish the condition.
Providers without usable native evidence retain the generic error fallback.
APS does not initiate downloads for verification. macOS also scopes Apple's
[dataless materialization opt-out](https://developer.apple.com/documentation/technotes/tn3150-getting-ready-for-data-less-files)
to synchronous identity I/O, restoring the thread policy afterward; a failed
read without positive dataless evidence remains generic.

The reason is transient, not cached proof: invalidation/manual retry clears it,
new failure evidence can re-establish it, and successful hashing omits it.
Existing Windows attribute/content events and macOS metadata/content events
refresh the entry after the customer downloads it, then normal settling and
hashing apply. Dormancy/bank changes discard it with the rest of the snapshot.
Lease, entitlement, pause and transport requirements are unchanged. Clients use
only public feedback, never native logs or remote filesystem/provider inspection.

##### Content hashing and aggregate digests

For an ordinary file, `sha256` is SHA-256 of its exact bytes. `size` and `mtime` are advisory metadata and are not digest inputs. Matching metadata alone does not prove matching content. Valid matching content hashes remain meaningful even if different copies have different mtimes.

Compute `folder_digest` from `(filename, ready sha256)` pairs as follows:

1. Preserve case and Unicode representation. Encode names as UTF-8 without BOM, normalization or locale transformation.
2. Sort lexicographically by **unsigned UTF-8 bytes**, with a shorter prefix first. Windows UTF-16 ordinal comparison is not equivalent for all Unicode characters.
3. Concatenate each name's actual UTF-8 bytes, one TAB byte (`09`), its 64 lowercase ASCII hexadecimal hash characters and one LF byte (`0A`). Include the final LF. Do not add CR bytes, an extra blank line, or JSON/backslash escaping.
4. SHA-256 the concatenation and encode the result as 64 lowercase hexadecimal characters.

TAB, CR or LF in names, and unsupported name encoding, produce an error instead of an ambiguous serialization. Empty input uses the ordinary SHA-256 empty-input value.

| Independent test vector | Expected SHA-256 |
| --- | --- |
| File bytes `abc` | `ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad` |
| Empty file or empty aggregate input | `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855` |
| Folder: `A.pptx` contains `abc`; `B.pptx` is empty | `e3af6991b918488b2353b6ca9e37e6434d7f6d69863577b2d5a97ca16525f3f5` |
| Package: `Data/a` contains `abc`; `Data/b` is empty | `721d44cdc85a15a39601114a69d1ef406af2a69ecc3d1e53318c21980271f0dd` |

A directory-form `.key` package is one outer entry. Its `sha256` uses the same aggregate algorithm over every regular descendant's package-relative path and whole-file hash. Include hidden descendants; use `/` separators without leading `/` or `./`. Directories and empty directories contribute no records. Unsupported objects or links make the package an error. Package size sums regular-file bytes; mtime is the newest regular descendant mtime, or the package directory mtime when empty. The outer folder aggregates the package basename and its resulting package hash. ZIP-form `.key` files use ordinary whole-file hashing; converting package representations or re-exporting is not guaranteed to retain the hash.

##### Settling, caching and live output

A detected content change invalidates the affected hash, including changes that preserve size and mtime; feedback may be coalesced. Native settling requires two seconds without relevant observed events and matching metadata checks one second apart. Package checks include full child membership and metadata, not only aggregate size/time/count. Hash work validates file identity/metadata before and after reading and when resuming.

`ready` describes observed stable content, not proof that an external writer has permanently finished. A writer can pause beyond the settling interval and resume later, invalidating the previous result. Neither metadata nor a checksum proves that a sync provider is currently working or that an application has reopened the latest file.

While enabled, the background serial hash worker pauses during presentation preparation, webpage opening/fullscreen preparation and APS Media Player video playback, for every file size. Ordinary presentation playback, including embedded media, audio, still images and paused/stopped video do not pause hashing. Native preparation gates close before work begins and reopen only after all active reasons clear. The worker retains offset/hash context across these pauses, revalidates on resume and restarts changed work. Metadata observation and already-ready unchanged hashes remain available while subscribed. System sleep clears leases and makes hashing dormant; a client must reacquire after wake.

Completed hashes are cached in memory only during uninterrupted observation of the same bank/root. Dormancy, restart and unobserved bank/root intervals require fresh hashes, including for same-size changes with restored mtimes. Cache representation and native filesystem identity are private implementation details. Unreadable files report `error` with a null hash and retry on a relevant event or explicit rehash. Recovery of an unavailable folder triggers reconciliation.

##### Compatibility with experimental observation builds

The experimental `watched_presentation_folder_observation` capability and its optional `observation_epoch`, `snapshot_sequence`, `content_revision` and `metadata_settled` fields were withdrawn from the current development implementations on 2026-09-12. Some development builds may still advertise/send them. Consumers must tolerate those additional fields and must not require them for the base details capability or checksum comparison. Their presence must not grant content verification or observed-convergence status.

Metadata can be reported before settling; matching size/time alone never proves matching bytes. Cross-machine display and show-readiness decisions belong to clients.

#### App permissions (macOS)

This read-only API v2 extension is available when `aps_info.data.capabilities` contains `app_permissions`. APS-Mac implements it; APS-PC does not need to implement or advertise it. Clients must feature-detect the capability, ignore unknown additive fields and capability names, and keep existing behavior when it is absent. No existing settings or commands change.

The parameterless command `{"command":"GetAppPermissions"}` requests the current cached snapshot and an asynchronous refresh. APS also sends `app_permissions` after `aps_info` in the initial connection snapshot, and broadcasts changed results over the existing framed TCP connections. No separate broadcast port or discovery record is used.

```json
{
  "action": "app_permissions",
  "data": {
    "effective": {
      "accessibility": true,
      "input_monitoring": "not_determined",
      "screen_recording": false
    },
    "system_settings": {
      "accessibility": true,
      "input_monitoring": "granted",
      "screen_recording": false
    },
    "probe_status": "available"
  }
}
```

- `effective` describes the access available to the running APS process. `accessibility` and `screen_recording` are Booleans; `input_monitoring` is `granted`, `denied`, or `not_determined`.
- `system_settings` has the same shape and represents readings from a freshly launched APS permission probe. It is `null` until a result is available and whenever the probe fails. These readings describe access granted to APS, not an enumeration of System Settings entries; in particular, Input Monitoring access does not prove that a separate Input Monitoring entry exists.
- `probe_status` is `pending` before the first result, `available` after success, or `unavailable` after failure. A later failure invalidates the previous `system_settings` reading. During subsequent refreshes the last successful reading remains available until the probe completes.
- A difference between effective access and the fresh-process reading means an APS restart is needed to apply the change. For this comparison, Input Monitoring `not_determined` and `denied` both mean not granted. If `system_settings` is unavailable, show effective access without claiming that no restart is needed. Clients must treat missing or unknown values as unavailable, never as denied.

APS shares one asynchronous probe between the native App Permissions window and network reporting. It refreshes every five seconds while API clients are connected, or every two seconds while the native window is visible. Activation and requests also trigger refreshes, coalesced to at most one probe start per two seconds, with no overlapping probes. Periodic monitoring stops when neither surface needs it. Unchanged results are not broadcast; connection snapshots and explicit requests always return the cached state immediately. Probe completion can produce a subsequent update.

Automation and File Access have no aggregate status in this extension, matching the native window's guidance-only sections; macOS can only answer for an Automation target that is running, so the separate event-driven [`automation_permission`](#automation-permission-macos) feedback below reports Automation problems at the moment APS tries to control an app. This API never grants or requests permissions, opens System Settings, restarts APS, or exposes file selections. Permission status is independent of licensing. To change permissions, use App Permissions in native APS on the presentation Mac; these are not writable `SetSetting` or `ToggleSetting` fields.

#### Automation permission (macOS)

This read-only API v2 extension is available when `aps_info.data.capabilities` contains `automation_permission`. APS-Mac implements it; APS-PC does not need to implement or advertise it. Clients must feature-detect the capability, ignore unknown additive fields and capability names, and keep existing behavior when it is absent. No existing settings or commands change, and there is no command for this feedback.

macOS grants the Automation (Apple Events) permission per target app and only answers for a target that is running, so APS checks the permission at the moment it is about to control an app and reports the result:

```json
{
  "action": "automation_permission",
  "data": {
    "app": "Keynote",
    "bundle_id": "com.apple.iWork.Keynote",
    "status": "denied",
    "reason": "open presentation"
  }
}
```

| Field | Meaning |
|---|---|
| `app` | Display name of the target app: `Microsoft PowerPoint`, `Keynote`, `Google Chrome`, `Adobe Acrobat`, `Skim`, or `System Events`. Clients must tolerate additional names. |
| `bundle_id` | Bundle identifier of the running target variant. Google Chrome betas and canaries report their own identifiers, all prefixed `com.google.Chrome`. Use this field to key per-app state. |
| `status` | `denied`, `not_determined`, or `granted`. `denied` means the operator declined the toggle in System Settings > Privacy & Security > Automation, or dismissed the macOS consent dialog, which macOS records as denied. `not_determined` means macOS will show the consent dialog on the first real command. `granted` means APS may control the app. APS never sends `not_running` or `unavailable`; those internal readings are logged locally for control, launch and connection checks, and remain silent during periodic verification. |
| `reason` | What triggered the check: `open presentation`, `open webpage`, `launch` (APS starting its System Events helper at launch), `connect` (a controller connected), or `verify` (periodic verification of an unresolved problem). Clients must tolerate additional values. |

Send policy:

- `denied` and `not_determined` are sent on **every** control attempt or connection check that finds them. Repeats are normal and let a client show that the problem is still current.
- `granted` is sent **once**, only after a previously reported problem for that app clears. APS does not report a grant that was never preceded by a problem.
- When a client connects, APS re-checks System Events and every target whose last reported status is still `denied` or `not_determined`, after sending the capability advertisement. Results are broadcast as ordinary feedback with reason `connect`; cached reports are never replayed verbatim in the connection snapshot. Connection checks never launch apps or wait for them: closed targets are log-only and remain unresolved until a later check. Targets already waiting for launch finish their existing check instead.

- While at least one client is connected, APS re-verifies unresolved problems about every 5 seconds with reason `verify` and sends only changes: a changed problem kind or one `granted` when it clears. A `granted` can therefore arrive without a control attempt, relaunch or reconnect. Periodic checks never launch apps or wait for them, skip targets already waiting for launch, and keep closed or unavailable targets unresolved without feedback or repeated log lines. Verification stops when all problems clear or the last client disconnects.

Grants are per code-signing identity, so a development build and a release build of APS have separate Automation entries in System Settings. A declined permission makes every AppleScript call to that app fail silently, which otherwise looks like a presentation that never started. This API never grants or requests the permission, opens System Settings, or restarts APS.

- `automatically_check_for_updates`: Whether APS automatically checks for updates.
- `installed_presentation_apps`: A fixed-order list filtered to detected apps. Possible values are `powerpoint`, `keynote`, `adobe_acrobat`, and `skim` on macOS; and `powerpoint`, `adobe_acrobat`, `adobe_reader`, `okular`, and `speedf` on Windows.

`media_player_above_still_images` is an optional additive API v2 setting. Feature-detect
`media_player_above_still_images` in `aps_info.data.capabilities` and require a Boolean
field in the authoritative `settings` snapshot before offering writes. General settings
support or an APS version number does not establish support. Missing capability or
missing/invalid field means unsupported/unknown, never `false` or an inferred platform
default. Older clients may ignore the new capability and field.

When `true`, APS Media Player visual output stays above APS Still Images output,
including Freeze, regardless of display order. When `false`, normal ordering applies:
the most recently displayed APS output can appear above the other ("last command wins").
This affects ordering only between these APS outputs, not still-image levels relative
to other applications, focus, activation, playback, fullscreen, or display selection.
Audio-only playback does not acquire a visual window. The native default with no saved
preference is **ON on macOS** and **OFF on Windows**; saved choices are preserved.

Supported APS builds include the authoritative Boolean in the initial connection
snapshot, `GetSettings`, and normal settings feedback. Local desktop edits and remote
writes use the same persisted runtime preference and notify connected clients. Changes
apply immediately to active outputs without restarting media. Clients must never write
a default on connection, page opening, reconnection, or selection of another machine.

For example, explicitly turn the setting off:

```json
{"command":"SetSetting","parameters":{"setting":"media_player_above_still_images","value":false}}
```

Or toggle the current native value (omit `value`):

```json
{"command":"ToggleSetting","parameters":{"setting":"media_player_above_still_images"}}
```

A successful changed explicit write returns:

```json
{"action":"settings_update_result","data":{"success":true,"operation":"set","setting":"media_player_above_still_images","changed":true,"warnings":[],"error":null}}
```

This result is followed by a complete authoritative `settings` message as above, with
`media_player_above_still_images` set to `false`. A same-value write succeeds with
`changed: false`; toggles report `operation: "toggle"`. Strings, numbers, null, a missing
set value, or a toggle containing `value` are invalid and leave saved/runtime state
unchanged. Existing settings error/result conventions and result-then-settings order
apply on success, failure, and no-op writes. Do not send these writes or retry them
against peers that do not advertise this feature.

##### Presentation font-checking setting

`check_presentation_fonts` is an optional additive API v2 capability and Boolean
field in `settings.data`. Require both before offering writes. Missing capability
or missing/invalid value means unsupported/unknown, never OFF. Implemented on
APS-Mac and APS-PC. Use capability detection, not a platform
or version check. Older peers keep their existing font behavior.

The native default is OFF when no choice is saved. The persisted setting is shared
by native Settings, Presentations > Fonts, and API writes. Initial snapshots,
`GetSettings`, local changes, and settings feedback after remote writes report the
current value.
Discard the prior value on reconnect and wait for fresh feedback. Never write a
default automatically on connection, machine selection, or opening a view.

```json
{"command":"SetSetting","parameters":{"setting":"check_presentation_fonts","value":true}}
```

To turn checking OFF, use `value: false`. To toggle the current native value:

```json
{"command":"ToggleSetting","parameters":{"setting":"check_presentation_fonts"}}
```

Set accepts only a JSON Boolean; toggle accepts no `value`. Existing
`settings_update_result` and complete authoritative `settings` feedback apply.
A same-value write succeeds with `changed: false` and does not start another scan.

An OFF-to-ON transition starts the same fresh background font check as the local
control. On Windows this uses the existing installed-font, Office cloud-cache and
catalog sources; it does not request permissions, download/install fonts or launch
PowerPoint. The full Office permission scan is Mac-only.
Tell the operator that any macOS access popup must be handled on the presentation
Mac. Remote enabling is refused with `unavailable_value`, leaving the setting OFF,
while a presentation (including a fullscreen webpage) or Media Player video is
showing. Clients should disable enabling from the corresponding presentation/video
feedback; APS remains authoritative. Disabling and no-op writes remain allowed
during a show. A successful settings write confirms the setting, not scan completion
or granted Office access. It does not create a `CheckOfficeFonts` request ID.

Turning OFF cancels active checks, clears cached presentation font results and
restart advice, and stops automatic checking. Re-enabling starts fresh observations;
saved positive Office evidence on macOS is retained. Windows keeps no such evidence
store. While OFF, remote `CheckOfficeFonts` (macOS only)
returns `unavailable` with reason `font_checking_disabled`, and `RestartPowerPoint`
fails at `precheck` with error code `font_checking_disabled`. A restart already
admitted is not interrupted by disabling.

**Remote font installation is independent.** The Network setting **Allow remote
font installation**, its read-only `font_installation_status`, and all existing
transfer/installation authorization checks remain unchanged. Turning checking OFF
neither blocks font installation nor revokes its grants. Installing a font while
checking is OFF does not turn checking on or resume scans.

#### Settings update result

APS sends this result after every recognized `SetSetting` or `ToggleSetting` request. It then sends a complete [`settings`](#settings) message containing the authoritative state, regardless of whether the write succeeded, failed, or made no change.

Successful change:

```json
{
  "action": "settings_update_result",
  "data": {
    "success": true,
    "operation": "set",
    "setting": "seamless_switching",
    "changed": true,
    "warnings": [],
    "error": null
  }
}
```

An explicit value that already matches the current state is successful with `changed: false`. `ToggleSetting` uses `operation: "toggle"`. State-change broadcasts can also occur during a mutation; the complete settings snapshot following the result remains authoritative.

Failure:

```json
{
  "action": "settings_update_result",
  "data": {
    "success": false,
    "operation": "set",
    "setting": "network_port",
    "changed": false,
    "warnings": [],
    "error": {
      "code": "read_only_setting",
      "message": "network_port can only be changed locally in APS."
    }
  }
}
```

- `success`: Whether APS accepted and applied the request.
- `operation`: `set` or `toggle`.
- `setting`: The requested setting name, or `null` when no valid string was supplied.
- `changed`: `true` only when the stored setting changed.
- `warnings`: Stable warning codes. On macOS, `screen_recording_permission_required` can be returned when remote control enables Seamless Switching without Screen Recording permission.
- `error`: `null` on success; otherwise an object with a stable `code` and a human-readable `message`.

Error codes:

- `invalid_request`: A required parameter is missing, has the wrong JSON type/value, includes a value with `ToggleSetting`, or tries to toggle a non-Boolean setting.
- `unknown_setting`: The setting name is not recognized.
- `read_only_setting`: The setting can only be changed locally or is derived by APS.
- `unavailable_value`: The requested display or application is not currently available, the value is a feedback-only fallback such as PDF `none`, or remote enabling of `check_presentation_fonts` was refused because a presentation or Media Player video is showing.

`powerpoint_restart` enables the [`RestartPowerPoint`](#presentation-application-commands) command and [`powerpoint_restart_result`](#powerpoint-restart-result) feedback; `presentation_folder_delete` enables [listing and recycling presentation-folder files](#presentation-folder-file-deletion); #### Licence status

When `aps_info.data.capabilities` contains `license_status`, APS sends an informational snapshot of the licence/trial mode it is currently enforcing locally. APS sends it during the initial connection snapshot and again whenever the state, deadline, transition reason, or closing flag changes.

Trial example:

```json
{
  "action": "license_status",
  "data": {
    "state": "trial",
    "trial_expires_at": "2026-08-05T15:20:00Z",
    "will_close": false
  }
}
```

Final feedback before APS closes because the trial ended:

```json
{
  "action": "license_status",
  "data": {
    "state": "trial",
    "trial_expires_at": "2026-08-05T15:20:00Z",
    "reason": "trial_expired",
    "will_close": true
  }
}
```

- `state`: `licensed`, `trial`, or `unknown`. `licensed` means APS is currently operating as licensed; it is not proof of a fresh online validation. `unknown` covers startup validation, incomplete selection, and inconsistent or unavailable local state.
- `trial_expires_at`: Present only for `trial`. It is the actual trial deadline as an RFC 3339/ISO 8601 UTC timestamp. Clients should calculate countdowns from this value rather than hardcoding a trial duration.
- `reason`: Optional transition reason. `license_invalidated` means a previously accepted licence became unusable; APS preserves its existing activation/trial flow rather than closing immediately. `trial_expired` means the local trial deadline was reached.
- `will_close`: Always present. It is `true` only in the final `trial_expired` feedback sent immediately before APS closes because the expired trial was not resolved.

This feedback is informational and uses the same best-effort LAN delivery as other APS feedback. It never contains a licence key, subscription identifier, customer information, or raw licence-server response, and clients must not use it to perform licence validation. A missing `license_status` capability means this feedback is unsupported, not that APS is unlicensed. This platform-neutral contract is implemented by APS-Mac and APS-PC.

#### Connected clients

Available when `aps_info.data.capabilities` contains `client_list`. APS-Mac implements this feedback in APS 4.5 and later; APS-PC implements it in APS 4.4.0.2 and later. See [Client identification](#client-identification) for the command that populates the client-declared fields and for the rationale.

```json
{
   "action": "clients",
   "data": {
      "clients": [
         {
            "connection_id": "c-17",
            "self": true,
            "address": "192.168.1.91",
            "connected_at": "2026-09-04T05:08:35Z",
            "client_kind": "aps-hub",
            "client_id": "9d1c3c2e-6a8f-4d0b-9b2e-3f5a7c1d8e40",
            "client_name": "Morten's MacBook",
            "client_version": "0.1.8",
            "roles": [
               {
                  "role": "sync-group",
                  "group": "Main room",
                  "locked_to_instance_id": "a1b2c3d4-e5f6-47a8-90ab-1234567890cd",
                  "locked_to_name": "Lenovo",
                  "reference": false
               }
            ]
         },
         {
            "connection_id": "c-18",
            "self": false,
            "address": "192.168.1.40",
            "connected_at": "2026-09-04T05:02:11Z"
         }
      ]
   }
}
```

- `clients`: Required array with one entry per currently open API connection, including the receiving connection. Ordering is insignificant.
- `connection_id`: Required string assigned by APS. It is unique for the lifetime of the APS process and is never reused for another connection, so anonymous clients that never sent `ClientInfo` (older APS Hub builds, Companion today, third-party controllers) remain distinguishable from each other. It is not stable across APS restarts.
- `self`: Required Boolean. `true` on exactly one entry: the connection that is receiving this frame.
- `address`: Required string with the remote IP address of the connection as seen by APS.
- `connected_at`: Required RFC 3339/ISO 8601 UTC timestamp of when APS accepted the connection.
- `client_kind`, `client_id`, `client_name`, `client_version`, `roles`: Client-declared fields copied from the latest [`ClientInfo`](#client-identification) received on that connection, after truncation to the documented limits. They are present only when that connection sent `ClientInfo`, and only the fields it included.

APS sends the complete list in the initial connection snapshot after advertising the capability, again whenever a connection is accepted or closed, and whenever a `ClientInfo` changes a connection's entry. Every frame is a full replacement; clients must replace their stored list rather than merge it. APS coalesces bursts of changes, for example many clients reconnecting after a network change, into at most a few frames per second; the last frame in a burst always reflects the current state.

Everything in this feedback is advisory. `connection_id`, `self`, `address`, and `connected_at` are observed by APS, but the client-declared fields are self-reported over the LAN and can be stale, missing, or wrong. Consumers may show the list to operators and warn about apparent conflicts, but they must not refuse to send commands, take control away from another client, or otherwise block an operator based on this feedback without a visible override. APS itself never uses the list to arbitrate between connections.

### Windows service discovery (DNS-SD/mDNS)

APS for Windows advertises its running TCP API on the local network through multicast DNS. Discovery is additive and best-effort: clients must continue to support manual IP entry when multicast DNS is unavailable or filtered by the network.

- Service type: `_aps-api._tcp.local`
- Instance name: `APS-<instanceId>._aps-api._tcp.local`
- SRV target: the Windows hostname reported by the same provider as `aps_info.data.hostname`
- SRV port: the TCP API listener's actual bound port
- Interface scope: all interfaces (`InterfaceIndex = 0`)

The TXT record contains UTF-8 string values:

| Key | Value |
| --- | --- |
| `txtvers` | Discovery TXT schema version. Currently `1`. |
| `id` | Persistent APS `instanceId`. |
| `name` | User-defined Windows `PC Tag`. |
| `host` | Windows hostname. |
| `platform` | `windows`. |
| `apsver` | APS application version. |
| `port` | Actual bound TCP API port, equal to the SRV port. |
| `apiver` | Integer APS TCP API version. |

APS publishes only after the TCP listener reports that it is bound. It removes and republishes the advertisement after API-port, PC Tag, instance-identity, network-interface, and sleep/wake changes. Consumers should therefore tolerate short remove/add sequences and goodbye records during normal operation.

DNS-SD may automatically suffix an instance name to resolve a name collision. The advertised label is not stable identity. A client must key candidates by TXT `id`, connect to the resolved TCP endpoint, and verify the same identity in the `aps_info` handshake. Unknown TXT keys must be ignored. Consumers should validate `txtvers`, try all resolved addresses, and treat mismatched SRV and TXT ports as stale or invalid discovery data.

### File transfer (HTTP):

APS on Windows and macOS runs a small HTTP/1.1 server that lets a client push a single file to the machine over the LAN. The port is advertised in [`aps_info`](#aps-info) as `file_transfer_port`; if the field is absent the endpoint is unavailable or unsupported. Base URL: `http://<aps-host>:<file_transfer_port>`.

Received files are published into the APS incoming folder (`%LocalAppData%\APS\Incoming` on Windows; `~/Library/Application Support/Auto Presentation Switcher/Incoming` on macOS).

General rules:

- **Single active session.** At most one transfer session exists at a time. A new `POST /files` discards any previous session and deletes its part file; the old `transferId` then returns `404` on every endpoint.
- While a transfer is in progress the file is written to a hidden part file named `.{transferId}.part` in the incoming folder. A partially transferred file is never exposed under its final name; on successful completion any existing file at the final destination is deleted and the part file is renamed into place (overwrite by destination).
- Requests and responses use JSON (`application/json`), except chunk bodies which are raw `application/octet-stream`. Error responses have the shape `{"error": "<message>"}`.
- Error message text is informational and may differ by platform. Clients must use the HTTP status and documented stable codes such as `offset_mismatch`, `overflow`, `size_mismatch`, and `hash_mismatch`, not human-readable wording.
- Chunk bodies are limited to 32 MiB (33554432 bytes); a larger declared `Content-Length` is rejected with `413` before the body is read. `Transfer-Encoding: chunked` request bodies are not supported (`411`).
- On per-id routes, an unknown `transferId` returns `404` **before** any body validation.
- `transferId` must match `^[a-zA-Z0-9-]{8,64}$`.
- File-name rules: the name must be non-empty after trimming, at most 255 characters, must not be `.` or `..`, and must not contain `/`, `\`, NUL, or the substring `..`. On Windows the receiver additionally rejects names that are invalid on NTFS: the characters `< > : " | ? *`, control characters, reserved device names (`CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9`), and names ending in a dot or space.
- When `file_transfer_relative_paths` is advertised, `POST /files` may include `relativePath`. It uses `/` as the wire separator on every platform, must be relative, must end with `name`, and every component must pass the same cross-platform name validation. Empty components, `\`, leading/trailing `/`, parent references, and destinations outside the APS incoming folder are rejected. APS creates missing subfolders only after the file hash has verified.
- There are no timeouts and no resume: chunks must be sent strictly sequentially. `GET /files/{transferId}` reports progress and is the primitive a future resume feature would build on.

#### POST /files

Starts a new session (discarding any previous one).

Request body:

```json
{
   "transferId": "b46f6f22-8f4c-4d9a-9d6e-2f6a5a2b9c1e",
   "name": "deck.pptx",
   "relativePath": "Sunday show/Slides/deck.pptx",
   "size": 1048576
}
```

- `size`: Total file size in bytes; a non-negative integer. Zero is allowed (create, then complete without sending chunks).
- `relativePath`: Optional folder-preserving destination beneath the APS incoming folder. Omit it for the legacy behavior of publishing directly into the incoming folder. Requires the `file_transfer_relative_paths` capability.

Responses:

- `201` `{"transferId": "<id>"}` — session created, empty part file written.
- `400` `{"error": "<message>"}` — invalid `transferId`, `name`, or `size`.

#### PUT /files/{transferId}/chunks

Appends one chunk. Headers: `Content-Type: application/octet-stream`, `x-offset: <bytes received so far>` (decimal, strictly sequential). Body: the raw chunk (max 32 MiB).

Responses:

- `200` `{"bytesReceived": <total>}` — chunk appended.
- `404` `{"error": "Unknown transfer."}`
- `400` — wrong content type or missing/invalid `x-offset` header.
- `409` `{"error": "offset_mismatch", "bytesReceived": <total>}` — `x-offset` does not equal the bytes received so far.
- `409` `{"error": "overflow", "bytesReceived": <total>}` — the chunk would exceed the declared `size`.
- `413` — chunk larger than 32 MiB.

#### GET /files/{transferId}

Reports session progress.

Responses:

- `200` `{"transferId": "<id>", "name": "<name>", "relativePath": "<optional relative path>", "size": <declared>, "bytesReceived": <total>}`
- `404` `{"error": "Unknown transfer."}`

#### POST /files/{transferId}/complete

Verifies and publishes the file. Request body: `{"sha256": "<64 lowercase hex chars>"}`.

On success the part file is verified against the declared size and the SHA-256 hash, any existing file with the same name is deleted, and the part file is renamed to the final name in the incoming folder.

Responses:

- `200` `{"verified": true, "name": "<name>", "relativePath": "<optional relative path>", "sha256": "<hash>", "path": "<absolute path>"}`
- `404` `{"error": "Unknown transfer."}`
- `400` `{"error": "A lowercase hex sha256 is required."}` — malformed hash (the session survives).
- `422` `{"verified": false, "error": "size_mismatch"}` — bytes received do not equal the declared size. The session and part file are discarded.
- `422` `{"verified": false, "error": "hash_mismatch"}` — computed hash differs. The session and part file are discarded.
- `500` `{"error": "<message>"}` — the destination file could not be replaced (for example it is open in PowerPoint). The session and part file are discarded; retry by starting a new transfer.

#### DELETE /files/{transferId}

Aborts the session and deletes its part file.

Responses:

- `204` — no body.
- `404` `{"error": "Unknown transfer."}`

### Presentation-folder uploads

Feature-detect both `presentation_folder_upload` in `aps_info.data.capabilities` and an advertised `file_transfer_port`. These operations add individual files to configured presentation-folder banks, including unwatched banks. They do not change the selected bank, incoming-folder setting, slots, or playback. Legacy `/files` remains unchanged.

#### PreparePresentationFolderUpload (API v2 TCP)

Send on a negotiated API v2 connection:

```json
{"command":"PreparePresentationFolderUpload","parameters":{"request_id":"request-123","bank_number":2,"name":"Talk.pptx","size":1048576,"mode":"create"}}
```

- `request_id`: correlation string, echoed in the requesting connection's response.
- `bank_number`: integer 1–20, resolved by APS to that configured bank's root. No absolute client-supplied destination is accepted.
- `name`: one validated cross-platform filename, not a relative path. No traversal, separators, Windows reserved names or directory/package/link destinations.
- `size`: integer byte count, 0 through 1099511627776 (1 TiB).
- `mode`: `check`, `create`, or `overwrite`.
- `conflict_token`: required for overwrite, from a prior create conflict on this connection for the same bank/root/name and unchanged existing file. Consumed by an overwrite attempt.

Response action: `presentation_folder_upload`; `data` always echoes `request_id`.

- Check: `{"status":"available"}` or `{"status":"conflict"}`; allocates no upload.
- Create collision: `{"status":"conflict","conflict_token":"opaque","overwrite_allowed":true}`. An open/preparing presentation has `overwrite_allowed:false`. A nonregular destination has `overwrite_allowed:false` and `error:"not_regular_file"`; it cannot be overwritten.
- Prepared: `{"status":"ready","transfer_id":"uuid","token":"secret","name":"Talk.pptx","overwrite":false}`. APS creates a private staging session outside the watched folder.
- Rejected: `{"status":"error","error":"code"}`. Relevant codes include `invalid_request`, `invalid_authorization`, `conflict_changed`, `file_open`, `folder_unavailable`, `not_writable`, `transfer_in_progress`, `busy`, and `io_error`. Consumers must tolerate other error codes and preserve a readable fallback.

Clients choose their own copy names (Hub uses `Talk copy1.pptx`, increasing to the first free number), checking availability through APS. They must obtain a new create authorization for the chosen name. Every conflict requires explicit operator choice in Hub.

#### Authenticated HTTP upload

Use `http://<APS host>:<file_transfer_port>/presentation-folder-files/<transfer_id>` with these headers on every request:

- `Authorization: Bearer <token>`
- `x-upload-sequence: <integer>`: starts at 1 and increases exactly by 1 for each authenticated request; do not replay a previously used sequence. Authentication/replay rejection is HTTP 403 `invalid_authorization`.

The secret stays with the controlling client; Hub keeps it server-side and never broadcasts it. Authorization is tied to its TCP connection and pinned destination. It expires after five minutes of inactivity, renews on authenticated HTTP requests, and is revoked on connection loss or listener shutdown. Completion or abort consumes the session. These are temporary transfer authorizations under the existing APS API control model, not a new pairing or user-authentication mechanism.

- `PUT .../chunks`: raw `application/octet-stream`, maximum 32 MiB per chunk, sequential decimal `x-offset`. Returns `{"bytesReceived":N}`. Offset mismatch and overflow return 409. No HTTP chunked request encoding.
- `POST .../complete`: JSON `{"sha256":"64 lowercase hex digits"}`. Returns `{"verified":true,"name":"Talk.pptx","sha256":"...","path":"absolute APS path","overwrite":false}` after size/hash verification and native publication. Size/hash mismatch returns 422 and discards staging.
- `DELETE ...`: aborts this transfer only and removes its staging data; returns 204. It does not delete a published file or clear a folder.

Publication revalidates the bank/root, destination snapshot and native open/preparing state. A create collision or changed target returns 409 `conflict_changed`, and an open destination returns 409 `file_open`. The client must return to preparation and fresh operator review. Missing/changed roots return `folder_unavailable`; write/replacement failures return platform-appropriate errors such as `publish_failed` or `io_error`. Existing destination data is not deleted before replacement. A failed completion ends the session; begin again to retry.

Native watcher feedback continues normally. Only supported presentation formats appear in its file list. Directory uploads, package reconstruction, automatic presentation close/reopen, synchronization and published-file deletion are outside this addition.


### Remote font installation

Feature-detect `remote_font_installation` in `aps_info.data.capabilities`.
Installation also requires an advertised `file_transfer_port`, a live negotiated
API v2 connection, and fresh explicit permission feedback. Missing capability means
unsupported; missing, stale, malformed or unknown permission means **not authorized**.
Existing file-transfer routes and generic settings retain their existing behavior.
An ordinary Incoming or presentation-folder upload never installs a font.

This utility installs standalone `.ttf` and `.otf` fonts **persistently for the OS
user running APS**, without elevation. It does not install for every user, alter
protected system fonts, or register fonts privately only inside APS. Files remain
in durable native storage. Collections, ZIPs, embedded fonts and downloaded/cloud
font acquisition are outside this API. APS validates actual SFNT contents and native
face metadata, not just the extension. Presentation font-warning text is advisory
and must not be parsed into installation requests or downloadable font identities.

#### Local permission and read-only feedback

**Allow remote font installation** is a local APS setting beside file-transfer
settings. It defaults OFF for new and existing installations. Only the local
operator can change it; neither `SetSetting`, `ToggleSetting`, nor another network
command can mutate it. Enabling it permits remote API clients to install fonts for
the current user. Existing file-receive enablement and network binding still apply.

This permission is independent of [Check presentation fonts](#presentation-font-checking-setting).
Font installation remains available under its existing authorization while checking
is OFF; toggling checking neither changes this permission nor revokes installation
grants. A completed installation does not enable font checking.

APS sends the dedicated feedback on API v2 negotiation/reconnect and on each local
permission change to every negotiated v2 connection:

```json
{"action":"font_installation_status","data":{"allowed":false}}
```

`allowed` is a strict Boolean describing the local permission, independently of
capability support and file-receive availability. Request a fresh snapshot with:

```json
{"command":"GetFontInstallationStatus"}
```

Clients clear permission on disconnect, reconnect, machine identity change and
capability loss; never carry a previous connection's `true` forward. Capability
advertisement describes implemented support and remains present while permission
is off. No polling is necessary; request another status after capability discovery
if the initial snapshot arrived before `aps_info`.

Clients disable selection/install entry points while permission is false or unknown,
including an already-open dialog, and show the reason outside disabled controls.
For false, use: “Remote font installation is disabled. Enable ‘Allow remote font
installation’ in APS's file-transfer settings on this computer.” There is no remote
permission switch. Native rejection remains authoritative regardless of displayed
client state.

#### PrepareFontInstallation (API v2 TCP)

```json
{"command":"PrepareFontInstallation","parameters":{"request_id":"font-1","name":"Example-Regular.ttf","size":102400,"sha256":"0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"}}
```

- `request_id`: nonempty correlation string, maximum 128 UTF-8 bytes.
- `name`: one validated cross-platform filename, maximum 255 characters, ending in
  `.ttf` or `.otf` (case insensitive). No paths, traversal, links or reserved names.
- `size`: integer 1–33554432 bytes (32 MiB), excluding Booleans/fractional values.
- `sha256`: exactly 64 lowercase hexadecimal characters; binds authorization to
  these specific bytes before uploading.

Only the requesting connection receives `font_installation` feedback:

```json
{"action":"font_installation","data":{"request_id":"font-1","status":"ready","transfer_id":"01874ffe-daf5-41e0-988d-35d409b5b6da","token":"opaque-secret","name":"Example-Regular.ttf"}}
```

Rejections have `status:"error",error:"stable_code"` and echo `request_id`.
`font_installation_disabled` means local permission is off; `file_transfer_disabled`
means the existing receive service is not available. At most one font upload/commit
is active per APS; another preparation returns `transfer_in_progress`. Submit
multiple selected files sequentially, with a separate preparation/result for each.
Preparing/selecting bytes does not install them; clients require an explicit Install
operator action identifying the destination computer and chosen files.

#### Authenticated font upload and commit

Use `http://<APS host>:<file_transfer_port>/font-installations/<transfer_id>`.
Every request includes `Authorization: Bearer <token>` and `x-upload-sequence`,
starting at 1 and increasing by exactly 1 for each authenticated request. Invalid
bearers/replays return HTTP 403 `invalid_authorization`. Rejected replay credentials
do not advance the sequence; other authenticated requests do. Bearers are bound to
the live granting TCP connection, font operation, name, size and digest. Tokens for
other upload purposes cannot authorize this route. Hub retains tokens on its server;
never log them or broadcast them to browsers.

Grants expire after five minutes of inactivity, renewed on authenticated requests,
and are revoked on TCP disconnect, receiver shutdown, or local permission revocation.
Turning permission back on never revives old grants. Native staging is private and
bounded; APS chooses all staging and durable storage paths. No client-supplied
installation path is accepted. Network bindings are exactly those of file receiving.

- `PUT .../chunks`: `application/octet-stream`, sequential decimal `x-offset`, raw
  body at most 32 MiB. Returns `{"bytesReceived":N}`. Wrong offsets/overflow return
  409 `offset_mismatch`/`overflow`. HTTP chunked request encoding is not supported.
- `POST .../complete`: JSON `{"sha256":"<same prepared digest>"}`. APS checks the
  prepared digest, received size/hash, and native font content. Size/hash failures
  return 422 `size_mismatch`/`hash_mismatch`. Completion consumes the grant, including
  failure; replay never repeats installation.
- `DELETE ...`: abort pending staging only; success returns 204. It never uninstalls
  a committed font and makes no rollback promise for a native commit already admitted.

After byte verification, completion returns a structured per-file result (HTTP 200):

```json
{"verified":true,"name":"Example-Regular.ttf","sha256":"0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef","status":"installed","faces":["Example-Regular"]}
```

Inspect `status`; **verified bytes do not mean installed fonts**:

| Status | Meaning |
| --- | --- |
| `installed` | Native persistent current-user installation completed. |
| `already_installed` | Identical installed face/content; no replacement or registration repeated. |
| `conflict` | An installed face/version conflicts; `error:"font_conflict"`. Nothing replaced. |
| `error` | Native validation/install failed; inspect `error`. |

`faces` lists validated PostScript face names, or is empty if validation failed.
`error:"invalid_font"` rejects malformed contents. `install_failed` means native
installation failed with no unrolled-back task-owned change; `partial_installation`
means some native state may remain and needs local inspection. Conflicts compare
face identity and content rather than filenames alone; v1 never automatically
replaces another version. APS cleans owned staging and rolls back owned partial
changes where safe, without altering unrelated/pre-existing fonts.

The stable error vocabulary also includes `invalid_request`, `unsupported_format`,
`invalid_authorization`, `io_error`, and `unknown_result`. Non-verified HTTP failures
use appropriate 4xx/5xx responses with `{"error":"code"}`. Clients must tolerate
unknown codes and provide a readable fallback, without parsing English error text.

Permission is checked at preparation and again at the serialized **native commit
boundary**, immediately before the first durable installation side effect. Revocation
invalidates queued/uncommitted work immediately. A transaction already admitted at
that boundary finishes and reports its actual outcome; turning the setting off does
not promise rollback. The operation runs off presentation-control/UI threads. A
successful install refreshes APS font-availability checks through the existing native
font-change/recheck path when font checking is enabled. If it is OFF, checking stays
OFF and no scan resumes. Hashing leases or verification entitlement are not required.

#### GetFontInstallationResult and uncertain completion

If a completion response is lost, query its receipt on the **same live TCP connection**:

```json
{"command":"GetFontInstallationResult","parameters":{"request_id":"font-read-1","transfer_id":"01874ffe-daf5-41e0-988d-35d409b5b6da"}}
```

The requester receives `font_installation` with the terminal result plus echoed
`request_id` and `transfer_id`. Failed completions also retain receipts. Receipts
are read-only, expire after five minutes, and are bounded to 128 globally (oldest
removed first). They remain readable when permission is revoked but disappear with
the owning connection. Unknown, expired or other-connection IDs return
`status:"error",error:"unknown_result"`; this does not prove nothing was installed.
Never retry installation automatically after uncertain completion. After reporting
the uncertainty, an operator may choose a fresh attempt; it must obtain new
authorization and pass normal duplicate/conflict checks again.

Always show near installation controls and results:

> Open presentations may not update immediately. You may need to reopen the
> presentation or restart PowerPoint or Keynote manually.

Installation success is not a guarantee of current presentation rendering. There
are no commands in this feature to reopen decks, restart apps, or change playback.

### Presentation-folder file deletion

Feature-detect `presentation_folder_delete` in `aps_info.data.capabilities`. Both commands use a negotiated API v2 TCP connection, independently of file-transfer ports or hashing leases. They operate on configured banks, including unwatched banks, without selecting a folder, clearing slots, or closing/reopening presentations. The existing upload-abort HTTP DELETE retains its original semantics.

#### ListPresentationFolderFiles

```json
{"command":"ListPresentationFolderFiles","parameters":{"request_id":"list-123","bank_number":2}}
```

`bank_number` is an integer from 1 through 20; APS resolves its configured root. No client-supplied filesystem path is accepted. Response action `presentation_folder_files` always echoes `request_id` to the requesting connection only:

```json
{"action":"presentation_folder_files","data":{"request_id":"list-123","status":"ok","files":[{"name":"Talk.pptx","size":1048576,"deletable":true,"token":"opaque-single-use-token"},{"name":"Open.pptx","size":2048,"deletable":false,"error":"file_open"}]}}
```

The list contains immediate regular files, including non-presentation formats and files added outside Hub. It excludes directories/packages, symbolic links/reparse points, invalid cross-platform filenames, internal `.aps-*` staging files and `*.apsprobe` files. `size` is bytes. Open/preparing files are listed but are not authorized for deletion. Each listing replaces that connection's prior deletion selections. Listings are bounded to 500 entries to fit existing framed-message limits; larger folders return `too_many_files`. Clients must handle an error instead of assuming an empty folder.

Tokens expire after five minutes and bind the requesting TCP connection, bank, root identity, filename and file identity/change metadata. Disconnect/listener shutdown revokes them. They are temporary operation authorizations under the existing APS API control model, not a new pairing/authentication mechanism. Hub retains native tokens server-side and exposes only opaque Hub selection IDs to its browser.

#### TrashPresentationFolderFiles

```json
{"command":"TrashPresentationFolderFiles","parameters":{"request_id":"trash-123","bank_number":2,"tokens":["opaque-single-use-token"]}}
```

Supply 1–500 distinct tokens from a current listing for the same bank and connection. Clients must obtain explicit operator confirmation identifying the machine, folder and selected filenames. Selecting all applies only to that reviewed snapshot; files subsequently added are not included.

```json
{"action":"presentation_folder_files","data":{"request_id":"trash-123","status":"ok","results":[{"token":"opaque-single-use-token","name":"Talk.pptx","status":"trashed"}]}}
```

Each authorized attempt consumes its token, including failed attempts. A failed item returns `status:"error"` and `error`, with `name` when the token was recognized. Relevant codes are `invalid_authorization`, `conflict_changed`, `file_open`, `folder_unavailable`, and `trash_failed`. Invalid envelopes return `status:"error",error:"invalid_request"`; listing failures may return `folder_unavailable` or `too_many_files`. Clients must tolerate unknown error codes. A successful envelope does not mean every file succeeded: inspect every item.

APS serializes deletion with upload publication, rechecks connection and bank/root/file identity, and refuses open/preparing targets. macOS moves files to Trash; Windows uses the native Recycle Bin and vetoes permanent deletion. Recycling/access failures leave the file in place; no permanent-delete fallback is offered. Recovery takes place on the APS computer. Normal watcher feedback continues, and clients should reload the list after an attempt. A timeout or lost connection means the result is uncertain: never automatically retry; reload and obtain a fresh operator decision.

Deletion targets one APS computer only. Customer-managed synchronization software may propagate the removal to other computers. This operation does not configure or control that software.
